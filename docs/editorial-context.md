# Editorial context for agents

Use one resolved private policy context before research or writing. Policy remains editable publication data; static skills describe how to fetch it.

```sh
papyrus editorial context --backend cloud --story STORY_LINEAGE --format json
papyrus editorial context --backend cloud --assignment ASSIGNMENT_ID --format text
papyrus editorial context --backend cloud --section SECTION_ID --format json
```

Everything the resolver needs is data in the site's cloud backend; no repository file is read. The publication is the backend's one canonical `KnowledgeCorpus` (role `canonical`): its ID gives the publication key and its current name the publication name, so the key is not a second setting that can drift from the corpus that holds the publication's topics. `--publication KEY` is optional and is only an assertion: it fails if it differs from the backend's key. Run from the publication's configured root with its existing authoring environment. A missing or ambiguous canonical corpus fails (the error names the fix: on a fresh backend run `papyrus publication init --key KEY --name NAME`, which creates the canonical corpus and is safe to repeat; it refuses to add a second publication to a backend that already has one). A backend deploy with `publication.reprojectOnDeploy` creates the corpus itself from the active brand's `corpusKey` and `publicationName` when none exists, and leaves a backend with a different publication alone; multi-canonical-corpus backends need an explicit publication ownership model before this resolver can support them, so it fails instead of guessing. Existing IAM authoring authorization is unchanged. This command configures no credentials, transport or endpoint.

Hosted resolution reads private, current mission and policy Items by canonical slugs (`editorial-doctrine-mission`, `editorial-doctrine-policy`, edited at `/newsroom/administration/policies`) and the current `NewsroomSection` mission, policy, assignment guidance and kill criteria (edited at `/newsroom/administration/sections`). These are the same records the Administration fields write; the same resolver feeds the copy-edit toolchain and the Cyclotron relevance and section-fit requests. Optional Assignment and story selectors resolve their section and reject contradictory scopes. Assignment snapshots cannot replace live policy. Missing, empty or ambiguous required publication policy is an error. Missing requested records and API authorization errors propagate; there is no local seed fallback. Empty optional section mission/policy slots produce warnings. This does not perform semantic conflict detection: the precedence instruction requires agents to surface conflicts in narrower assignment instructions.

Tenant selection comes from the existing configured client/environment, never a request parameter. Every consumed doctrine, story and section must match that scope, including rejecting tenant-stamped records when no tenant is configured. Tenant doctrine uses the existing tenant-slug index. Assignments have no tenant field; a tenant assignment therefore requires its linked story or section to establish scope. Brief/instruction attachments must belong to the requested Assignment; missing storage, empty content, ambiguity and read failures stop resolution. These checks constrain this resolver and do not replace backend authorization.

Repository YAML (`corpora/*-publication-doctrine.yml`, `corpora/*-newsroom-sections.yml`) is only a one-time import into the database (`papyrus sections import-doctrine`, `papyrus sections import`). The import creates what is absent and never overwrites a record that exists, so it is safe to re-run and cannot undo a newer edit made in the newsroom.

To edit them from the command line, use `papyrus sections doctrine set --kind mission|policy --file <md>` (the topic-steering workspace's doctrine save) and `papyrus sections update --id <section> [--editorial-mission-file F] [--editorial-policy-file F] [--assignment-guidance-file F] [--kill-criteria-file F] [--enabled true|false]` (Administration > Sections). Both take `--dry-run`.

The `editorial-context/v1` response includes publication and scope, ordered entries, source IDs/revisions/timestamps/content hashes, precedence, warnings, render version, `contextHash`, `resolvedAt` and generated `text`. The hash covers the rendered content and provenance, excluding fetch time. `--max-characters` fails if required text exceeds its limit; it never trims policy. Record the hash and source revisions in the story's reporting Messages. Private doctrine shapes editorial decisions; it is not evidence to quote in reader copy.

## Workers and existing API

`prepare_editorial_worker_input` resolves live context before the research/reporting and story-cycle procedure dispatches. It overrides caller-supplied policy fields and supplies text, hash and full provenance JSON in the run input. Standard researcher, reporter and copywriter procedures require text/hash and prepend them to the agent message, including retries. A direct procedure caller must fetch the same resolved context and provide those inputs. This is a clean contract change: updating local procedure source does not update already-stored ProcedureVersion rows. Release/review owners must synchronize procedure versions through the normal approved workflow; this change performs no seeding or deployment.

The Tactus host exposes `editorial_context{ assignment_id = "..." }` (also optional `section_id`/`story_lineage_id`) and `papyrus.editorial.context`. Existing Assignment context uses this resolver; the evidence pack includes its rendered text as one required block and fails if compaction drops required blocks. Source resolution is deterministic; no model calls are made to assemble policy.

GraphQL source exposes `getEditorialContext(publicationKey: String!, sectionId: ID, storyLineageId: ID, assignmentId: ID, maxCharacters: Int): AWSJSON`. Its JSON response is the same complete rendered/provenance contract as the CLI. `getAssignmentContext` and related queue contexts also return it in required `editorialContext: AWSJSON`, alongside doctrine summaries derived from that pack. The API uses the existing private assignment handler and the same authoring groups as assignment context. No public/guest route, public file or cache is added. The handler takes the endpoint from its existing generated backend configuration and tenant from its existing environment. Source schema and handler changes require the normal separately approved release; no deployed API availability is claimed here.

Both runtimes test the same synthetic contract fixture, including non-ASCII character counts, source revisions, generated text and canonical SHA-256 hash. Hashing uses recursively sorted compact JSON with UTF-8 text; `resolvedAt` is excluded. Adapter tests cover pagination, publication/tenant mismatches and attachment failures. The TypeScript test needs no Python environment or model access.

## Copywriting

Editorial checks are core to every site and on by default. A publication turns them off, or changes how they run, in its stored `EditorialCheckSettings` (Administration → Editorial checks → Settings; `enabled` defaults to true when no record exists). Disabling stops `checkEditorial` and `suggestEditorialRewrite`; the function and its IAM grants ship regardless. See `docs/editorial-checks.md`.

The static `.agents/skills/copywriting/SKILL.md` fetches this context and delegates copy editing to the editorial-checks cycle. The cycle loads both authenticated `editorial context` and `editorial pack`; doctrine and Humanus controls are complementary. `pack`, `check` and `suggest` now fetch current private context as part of request construction. Publication/section doctrine enters rewrite house guidance and every judgment detector's question instructions, while same-key section `EditorialPolicy` controls retain their replacement semantics. The effective context hash is included in the pack version. Humanus therefore invalidates its request cache when the policy text changes, even for unchanged draft text.

The editorial-checks function resolves exactly one canonical publication from its configured backend and invokes the existing private `getEditorialContext` query. Returned publication, section, tenant and context hash must match. Missing, denied, ambiguous or mismatched guidance stops the operation; there is no seed fallback or public policy endpoint. Source wiring adds only `listKnowledgeCorporaByRoleAndName` and `getEditorialContext` reads to this existing function's scoped GraphQL policy. Those permissions and the updated function require separately approved deployment; source tests do not establish live grants or rollout. Explicit `--pack` file mode remains offline and is labelled local rather than current hosted doctrine.

The assignment handler also requires Amplify's function data registration in the site schema to supply the generated endpoint/model-schema references needed by `getAmplifyDataClientConfig`. At synthesis, `scopeAssignmentDataAccess` replaces the SDK's broad GraphQL grants on this role with named fields for the existing lifecycle/context handler and its fixed reference-registration/provenance helpers. Unrelated administration, policy edits, publishing, deletes and subscriptions receive no grant; other function roles are untouched. The single model-schema object read and five exact resource-reference parameter reads remain. These are separate proposed permissions on the assignment role, beyond the editorial-checks role's two query reads. Review the synthesized consumer diff before deployment; no handwritten environment fallback or production permission change is implied. `npm run test:assignment-data-access` verifies required and excluded fields, preserved generated configuration and offline data-client initialization with synthetic resources.

No editing option is applied without a person choosing it. Save substantive article revisions as new Papyrus versions and keep citation promotion independent from classifier feedback. Keep real doctrine, examples and request text private; public tests use synthetic guidance only.

## Classification requests

Relevance and section sweeps preflight current database context before claiming or changing the engine. Each prepared item contains scoped context hashes so a policy update invalidates the engine's stable-decision cache without replacing its learned rubric. At the model boundary current policy is re-read, checked against those hashes and placed ahead of supplementary learned criteria. A mid-flight policy update stops transmission rather than sending stale guidance or silently retrying. Each section fit classifier receives its own context; the section selector intentionally receives the selected section set. Disabled and dry-run sweeps remain non-executing.

This wiring covers the Papyrus sweep request constructors. A separately composed remote publication host must bind the same trusted context adapter at its model boundary; merely sending a browser-supplied policy field is not equivalent. No remote host, execution switch, training run or provider activation is installed by this change.
