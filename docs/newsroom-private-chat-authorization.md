# Publication-local private chat authorization

The private chat host uses the existing newsroom Cognito access token. The server verifies signature, configured pool issuer and app client, access-token use, expiry and editor/admin group. Reader sessions are not sufficient. Chat does not request a Prospectus login, Account selection or entitlement. Other Prospectus features keep their own authorization.

The server derives a publication namespace from its configured private session bucket, messaging table and verified configured app client. A versioned `papyrus-newsroom-v1-` tenant includes this namespace and issuer; a `papyrus-newsroom-editor-v1-` editor includes that tenant identity and immutable issuer/subject. Differently authorized publications must not share the complete storage/client/issuer tuple; a shared frontend for the same publication is the same boundary. Deployment review must verify the configured resources and gateway role against the intended publication. Neither request host nor browser-provided Account, tenant, author, email or route context chooses the namespace. Replacing these resources or the configured client changes the namespace; migrating history requires an explicit reviewed mapping, never an automatic fallback.

Each private channel enforces tenant and participant access through the shared core, including messages, events and streams. Existing Prospectus-derived and legacy histories remain untouched and inaccessible through this new namespace. No canonical person association is inferred. Storage retention is unchanged.

Every request verifies its supplied token. Streams close at token expiry, and reconnects must reauthorize. Group claims remain valid until the access token expires; removal of a group or revocation of a refresh token does not instantly invalidate an already issued JWT under local cryptographic verification. The client obtains its current access token for each request, reopens and reauthorizes the conversation after a successful token refresh, and clears displayed history/retry state on sign-out, sign-in, failed token refresh or an authorization rejection. A previously admitted model turn can finish and persist its result; this does not grant future read access to a revoked editor. No token enters the queue or transcript.

The pinned site-hosted worker uses the computerless execution profile. Its shared extension supplies the system prompt and channel-note tool only; task/board/computer tools and Prospectus or editorial operations are not installed. New assistant records have empty memory. Model sessions are scoped by tenant, bot and channel, not shared across editors. Future context or editorial tools need their own server-side authority and scope review.

Regression coverage includes real signed synthetic-JWKS token validation, gateway denial before storage, no-cookie admission, cross-publication/editor and old-namespace denial, expiry and stream closure, scripted worker reply/replay persistence, and browser recovery/mobile interactions. These fixtures do not prove a live provider reply. Deployment acceptance must separately use a legitimate editor session, a clearly labelled message, an actual model response and refreshed persisted history.

Other account-scoped operations are authorized by Prospectus, fail closed, behind a per-site flag: see [CLI login: Authorization](cli-login.md#authorization).
