# Announcement and Delivery records

Status: records, indexes and relation types (PPY-3792dd, slice 1 of epic PPY-a36492), the attempt log (PPY-a570e8, slice 2), the review policy (PPY-97c0f2), the Story drawer and Announcements list (PPY-e4ae3a) and the editing window (PPY-e8ec54), and X on these records (PPY-efd06c: eligibility, drafting, the budget guard, dry run, withdraw, and the deletion of a corrected post); cloud only, X is off everywhere and nothing sends until the Caducus `x` channel is deployed and the owner turns it on. Design: `~/Projects/papyrus-announcement-delivery-design.md` sections 2, 2.1, 2.2 and 13.

Two records replace "one row for each announcement on each channel":

- An **Announcement** (model `AnnouncementDecision`) is the decision to say something about one or more Stories. It has a once-only key, a kind, a release time and a state. It knows nothing about channels, holds no approval and no words.
- A **Delivery** (model `Delivery`) is one channel's version of that decision: the account, the words and picture (files in S3), the approval it runs under, every wait as a named time, the attempts and the address of the result.

The model is named `AnnouncementDecision` (the name stays). The model `Announcement` that was the X row shape built for PPY-09ee86, with its account index and its round suffix, is deleted by PPY-efd06c; nothing migrated, because no live X row existed. See [announcements](announcements.md).

## The rules

- **Decided once.** An Announcement's id is made from its once-only key (`story-published:<lineage>`, `roundup:<list>:<yyyy-ww>`, `correction:<lineage>:<version>`) and the row is created with a condition on that id. The same Story published twice finds the first decision. The key is also an index, for reads from outside the writer.
- **Written together, finished on retry.** `Announcements.announce` writes the Announcement, then each Delivery and its words, then the `announces` relations. A crash anywhere leaves rows the same call completes. A decision with no Delivery writes nothing, so a publish that qualifies on no channel leaves no row. A plan that breaks a rule is refused before the first write.
- **One live Delivery for each Announcement, channel and account.** A Delivery's id is `<announcement>#<channel>#<account>#g<generation>`, created with a condition. A second Delivery for the same three is a correction: `Deliveries.supersede` writes the next generation with `supersedes`, marks the old one `superseded` with `supersededBy`, and writes the `supersedes` relation. AppSync has no transaction across writes, so these are three ordered conditional writes and a retry finishes them from a fresh read of the old row (a crash after any of the three is finished by calling `supersede` again with the same words). Only a Delivery that was sent is corrected (`NotSent`): one that never went out is edited, not corrected, and a draft with no words gets its first words from `Deliveries.write_words` on the same row. A different correction is a conflict, not a retry: when the successor already exists and its content hash differs from the new words, `CorrectedDifferently` says someone already corrected it and nothing of the second caller is written, so two corrections made at once leave one winner and one conflict. The live Delivery of a channel and account is the highest generation. Specs: `features_backend/delivery-corrections-hardening.feature`.
- **Approval lives on the Delivery** (`approval`, `approvalPolicy`, `approvedVersion`, `approvedBy`, `approvedAt`). `none` is approved by `system` under the named policy. An approval names one version; a later version is not approved. The Announcement keeps only the decision and `releaseAt` (UTC; empty means now).
- **Every wait is a named time on the Delivery.** `releaseAt`, `lockAt` (equal to `releaseAt` with no separate lock), `nextAttemptAt` with `waitingFor` (`rate limit`, `budget cycle`, `release`). `dueAt` is the earliest still pending, and with `dueKey` it is present only while one is, so the due index is sparse. A lock is a fact (`lockedAt`, `lockedVersion`); nothing holds it.
- **No text in the catalog.** A Delivery row holds `textKey`, `imageKey` and `contentHash`. The words are one file in S3 (a ModelAttachment, owner kind `delivery`, role `delivery_text`). `records.require_catalog_only` refuses a row that carries post text, HTML or Markus.
- **A change to a row is conditional on its `revision`**, so two writers never silently overwrite each other; the second is told the row changed (`Conflict`).

## Durable triggers (PPY-e3bb2b)

Two facts start an Announcement: **a Story's page is live** and **a Story's rating changed**. Both are changes to the Story's own `Item` record, so the Item change feed ([automations.md](automations.md#the-listener-index-and-the-item-change-feed)) delivers them to the announce agent as wakes on the site's wake queue, and nothing else does. A publish used to tell the newsletter and notifications functions with a short call whose every error was swallowed, which kept publishing fast and could lose the event; the once-only key cannot help an event that never arrives. That call (`publish_alerts.announce_published`), the variables that named the two functions on `content-actions` and the grants that let it invoke them are deleted, and no other path replaced them.

- **Which record marks "the page is live":** the Story's Item row entering the `published` stage (`Item/stage_entered` with `stage=published`). `publish_item` writes that stage in the same update that makes the version the lineage's current one, so the feed sees every publish: the console, the command line, an agent, a scheduled publish. The page's files are projected just after that write; an Announcement is a decision whose Delivery waits for its release time, its review and its send, and the worker checks the `PublishedItem` row before it decides, so a Story unpublished since the wake is not announced.
- **Which record marks "the rating changed":** the same Item row, when its `starRating` is set, changed or cleared in place (`Item/rated`, new). A new version that only carries the rating over is no change. The wake key names the stars and the moment (`announce|<lineage>|<version row>|rated.<stars>.<time>`), so rating again is a new wake and a stream record delivered twice is the same one.
- **The announce agent** (`agent_definitions/core/announce.yaml`, procedure `announce_story`, `list_cadence/story_wake.py`) listens for both, filtered to `stage=published`, so the feed's listener index sends it nothing for a draft. It runs one wake at a time (`serialBy: agent`). The wake says only what happened: the worker **re-reads the Story and re-checks everything** as it is now (page live, rating, each list's rule and floor, the policy's rung) and then makes the one Announcement `story-published:<lineage>` and its email Delivery, or says in a reason code why it made nothing (`story_not_published`, `no_list_carries_story`, `already_decided`). A rating change is what makes an unrated Story eligible; a later rating finds the Announcement already made.
- **Once, however it arrives.** The wake key makes a duplicate stream record one run (the run record is the claim and the queue deduplicates for five minutes); the once-only key makes a republish, a second rating and a retry after a crash find the first Announcement. A publish whose first delivery fails is still announced: the feed reports the record failed, Lambda redelivers the batch, and every key is the same.
- **Latency.** A publish writes only its own records (`PUBLISH_MODELS` in `publish_trigger_test.py`); the feed and the worker run after it, off the publish path.
- **No new table.** The change stream, the once-only key and the wake queue are the path.

Specs: `features_backend/announce-durable-triggers.feature`, `announce-agent-definition.feature`, `item-change-feed.feature` (the `rated` change).

**Not wired yet.** The real services of the `announce_story` run need the site's tenant and bucket from the runner (`procedure_runner.child_environment` now passes them) and a drafter for the words of an every-item email (PPY-64378c); until one exists the agent runs at `observe` and a run at `prepare` or above stops with that said in words. The email channel's one sending account is the site's own, named by its tenant.

## Attempts

A retry is an attempt. A Delivery's `attempts` field is a log that only grows; each entry has `number`, `at`, `eventId`, `outcome`, `code` (the provider's code) and, once closed, `closedAt`. Code: `attempts.py`; specs `delivery-a-retry-is-an-attempt.feature`, `delivery-attempt-written-before-the-call.feature`, `delivery-attempt-opening-guard.feature`, `delivery-one-consumer-per-account.feature`.

- **One event for each attempt.** Attempt N is the Caducus event `delivery:<deliveryId>:a<N>` (`channel.attempt_event_id`). Caducus dedupes on the event id, so the same attempt handed over twice posts once, and a retry is a new event. There is no round suffix: the X row shape's event id is also `delivery:<announcementId>:a<N>` (its `attempt` field), and Caducus 0.3.0 takes it as it is (`attempt-event-id.feature` sends through the released Caducus).
- **Written before the call.** `Attempts.open` writes the entry as `started` and moves the Delivery to `sending` in one write conditional on the row's `revision`; only then is the provider called. An entry closes `sent`, `refused` or `unknown` (the always-on standard's words). A `sent` or `refused` entry never changes; `unknown` closes once to one of those.
- **Settled, never timed out.** An entry left `started` or `unknown` is settled by reading Caducus's record of its event id (`Attempts.settle`). A record that says how it ended closes the entry. With no record the same event id is handed over again (Caducus dedupes, so no second post). With a record still queued nothing changes: no clock decides. Until then the list reads "Outcome unknown" (`attempts.shown`). A second attempt does not open while one has no answer.
- **A wait ends an attempt.** A pause closes it `refused` with code `paused` and the Delivery is `blocked` until a person resumes it. A budget stop closes it `refused` with code `budget reached`: `blocked`, with `waitingFor` `budget cycle` and `nextAttemptAt` when the cycle begins. A rate limit closes it `refused` with code `rate limit`: `ready`, with `waitingFor` `rate limit` and `nextAttemptAt`, which must name a time. `dueAt` follows `nextAttemptAt`. The next try is the next attempt. After the first attempt the release and lock times are used up and stop being pending.
- **No invented retry count.** A sequence ends on a clear answer: `sent`, a provider refusal (the Delivery is `failed` until a person tries it again), or the read that shows whether the post exists after an unknown outcome.
- **The guard when an attempt opens.** The Delivery must be the highest generation of its Announcement, channel and account, must not be superseded, and its words file must exist and match the row's content hash. Otherwise nothing is sent and one flag (subject type `delivery`) is raised, once for each Delivery and reason. A Delivery that is only waiting (not due, not approved, already sent) raises no flag. `releasable` still reads only the row.
- **Closing never revives.** A close applies to the row as it is now (it re-reads after a conflict). If the Delivery was superseded while its attempt was open, the outcome goes in the log, the provider's facts (`providerId`, `cost`) are recorded, and the state stays `superseded`.
- **A Delivery with an open attempt is not corrected** (`OpenAttempt`): settle it first. This is checked before the sent check, so the answer names the open attempt.
- **One worker for each channel account, for every channel.** All attempts for one channel account pass through one `AccountWorker`, which refuses a Delivery of another account. The queue that gives it a single consumer belongs to each channel's infrastructure and arrives with the Caducus release; X's worker is `x_runner.XRunner`, which refuses to send unless the site's mode is On.

Caducus needs no change to accept the id shape (its event id is any non-empty text it dedupes on); it has its own spec for `delivery:<id>:a<N>`.

## Counts (PPY-b53c09)

Caducus keeps the record of each reader; an email Delivery holds counts only. `counts` is eight numbers of readers (`queued`, `sent`, `failed`, `suppressed`, `skipped`, `delivered`, `bounced`, `complained`) and `cost` is what Caducus charged. Code: `counts.py`, `email_channel.py`, `sends.py`; specs `delivery-counts.feature`.

- **Recomputed, never added to.** `DeliveryCounts.refresh` reads Caducus's delivery-log rows of every attempt's event and writes the totals when they changed. `AccountWorker.send` and `settle` do it for an email Delivery, and `AccountWorker.refresh_counts` does it later, because the provider reports delivery, bounces and complaints after the send.
- **`sent` is every message the provider accepted.** `delivered`, `bounced` and `complained` are what became of them. A reader is counted once, by the row that says most about them.
- **Suppression is Caducus's, at send time.** A reader suppressed when their turn comes is counted `suppressed` and not mailed; a reader who turned the list off is `skipped`. A complaint or a permanent bounce also takes the reader off every list, so later sends never reach them, and Caducus records no row for a reader who is not a confirmed subscriber of any list of the event. A reader on two lists of one Delivery is one delivery (Caducus keys it by event, reader and channel).
- **No reader on the row.** The row holds no address, no pseudonym and no words.
- **Today.** `todayOverview` returns `sends`: one line for each email Delivery of an Announcement released in the day (lists, items, state in words with a mark, counts, cost), read by index (`sends.py`).

## Review policy (PPY-97c0f2)

Human review is a per-publication setting, not a rule. `announcementReview` is the announce responsibility's rung in the site's agent policy document (`src/papyrus_content/announcements/review_policy.py`; ladder in `src/papyrus_content/agent_policy/`): `hard` is `prepare` (a person must release it), `soft` is `publish_soft` (a person may edit or stop it before its lock time; silence lets it go), `none` is `publish_auto` (fully automatic). A rung below `prepare` prepares no Delivery, and the result says why. There is no second setting and no code default: an `announce` entry that is not in the document means off.

- **Overrides, narrowest wins:** the publication, then a channel, then an Announcement kind, then a list (newsletters). Each is optional, and they are the ladder's overrides, so one resolver answers every responsibility. A kind override beats a channel override (the ladder ranked them the other way round until this slice).
- **Written to each Delivery.** The value chosen is the Delivery's `approval`, and `approvalPolicy` says where it came from and the policy version, for example `override: kind roundup (agent policy version 4)` or `publication policy (agent policy version 4)`. It applies to Announcements made afterwards; a Delivery keeps what it was made under unless an editor changes that one (`Deliveries.change_approval`, the operation `announcements_delivery_review_set`), which then reads `set for this Delivery by <person>`.
- **`requireReviewedSource` is not a rung.** It is a condition on the input, in the announcement settings (`rules.requireReviewedSource`, off unless a person turns it on, `papyrus announcements settings set --require-reviewed-source`). When on, `intake.announce_story` makes an Announcement only for a Story a person has reviewed on its current version: the Story's checklist step `review_people` done by a person against that version number (`ChecklistReviewStamps`). **PROVISIONAL: Ryan has not confirmed this definition of a human review stamp** (a person, not an agent, marked `review_people` done, against the Story's current version); the held reasons, `papyrus announcements explain` and the settings help say so wherever the rule is shown (`intake.PROVISIONAL_NOTE`). A Story edited after its review has no stamp until a person marks the step again, and a Delivery whose Story changed goes back to a draft and is made ready again only once the Story is reviewed (`intake.make_ready`).
- **Floors under every policy.** A Story with no rating or under three stars is never announced, and a five counts only when a person gave it (`intake.floor_refusal`).
- **What a person and an agent may do** is rows of the one operation table (`announcements_*`, group `announcements`): an agent may release under `none` (rung `publish_auto`), is told `human_required` under `soft` or `hard`, may draft from `draft` and correct from `prepare`, and is `blocked` from changing a pinned block, the review policy or the budget. `announcements_review_set` sets the publication's value or one override (admins who are people only); `none` is refused while the ladder's hard floor for doubt (PPY-36e7c9) is missing, as `agents set-rung` refuses `publish_auto`.
- **In the list:** `review_policy.approval_label(row)` gives the words and a mark for each Delivery (`Released automatically by publication policy` with `bot`, `Released by a person (ellie)` with `user-check`, `Goes at its lock time unless a person stops it` with `hourglass`, `Waits for a person to release it` with `hand`). The console list that shows them is the Announcements list below.
- **Post spacing, per account.** The owner may set the minutes between one post and the next on one channel account, in the announcement settings (`spacing`, keyed `<channel>#<account>` such as `x#handle`; `papyrus announcements settings set --input-file` with `{"spacing": {"x#handle": 30}}`, `null` takes an account's spacing away). It is empty by default and empty means no spacing, so nothing is held. When it is set, `AccountWorker` (given the account's minutes) refuses to open the next attempt while the account's last post, or last attempt with no answer yet, is closer than that: the Delivery stays `ready`, `waitingFor` says `post spacing`, `nextAttemptAt` names when the spacing ends (so `dueAt` follows and the list shows the wait), and it goes like any wait once the time has come. Spacing is read from the account's own Deliveries, newest first by when each was made, stopping at the first with a post attempt (`Deliveries.last_post_at`); a Delivery that was made earlier but posted later than a newer one is not seen, which a durable last-post time on the account would fix and which needs a model field. Spacing is the owner's: `settings set` is a person only.
- **Specs:** `announcement-review-policy.feature`, `announcement-review-floors.feature`, `announcement-review-permissions.feature`, `announcement-human-review-stamp.feature` (PROVISIONAL definition), `announcement-post-spacing.feature`, and the settings scenarios in `announcement-settings.feature`.
- **Not built yet, and why (PPY-97c0f2 stays open).** Setting `none` through `set-rung` stays refused until the hard floors at every rung exist (PPY-36e7c9). `requireReviewedSource` stays publication-wide until channel and list rule objects exist.

## The Story drawer and the Announcements list (PPY-e4ae3a)

One Announcement, one line for each Delivery, in words and marks. `lines.py` says every word and names every mark (a Lucide icon), so the console, `papyrus announcements` and the agents' tools show the same sentence; `components/announcement-marks.tsx` draws them, and `announcement-list-marks.feature` fails if the backend can say a mark the console does not draw. A state is never colour alone, and the fills have no borders.

- **The drawer** (`components/announcement-lines.tsx`, `StoryAnnouncementsCard`, in the Story editor under the schedule) reads `announcements_where`: the Story's Announcements through the `announces` relation (one object-state index query), then one Announcement get and one Deliveries query for each, and shows one line for each live Delivery. A correction shows only the live generation.
- **The list** (the Announcements card of Administration > Announcements) reads `announcements_recent`: Announcements newest first from the planned-by-release-time index (one partition for each state, merged), each one's Deliveries from the Deliveries index, and what is overdue from the sparse due index. A page is a page size, not a cap; it ends where the release time changes, so Announcements released together are never split, and `next` is the release time to ask `before` for the page after it (the index starts below it as a key condition).
- **Each line says** its state (`Draft`, `Ready`, `Sending`, `Blocked: check failed`, `Sent`, `Failed`, `Dry run: not sent`, `Withdrawn`, `Superseded by a correction`), its review (`approval_words.py`: `Released automatically by ...` with `bot`, `Released by a person (...)` with `user-check`, `Goes at its lock time unless a person stops it` with `hourglass`, `Waits for a person to release it` with `hand`; none for a Delivery that will not go), what it waits for (a named time), and its last attempt.
- **Overdue** is a Delivery whose `dueAt` has passed (before now, not at it) and which has no attempt: the schedule did not wake it. It is read from the sparse due index, and a draft blocked by a failed check has no due time, so it is never overdue.
- **Outcome unknown** is a Delivery with an attempt that has no answer (`started` or `unknown`). It stays until Caducus's record settles it (`Attempts.settle`); no clock decides, so it reads the same a week later.
- **A blocked draft asks once.** `Deliveries.block_draft` blocks a draft whose checks failed (`blockedReason` `check failed`, nothing pending) and `blocked_drafts.block_and_flag` raises one review request, a flag, for the Announcement, with an id made from the Announcement's id: a second channel's failed check finds the first flag. The drawer and the list read it with one get by that id and show it once for the Announcement, with `flag`; an answered flag is no longer shown. The drafting that fails the checks arrives with the X rewire (PPY-efd06c), which calls `block_and_flag`.
- **`papyrus announcements explain --story X`** (`explain.py`) answers why a Story was or was not announced, for each channel, naming the rule: `announced`, the channel's own rules (`off`, `not_published`, `type_not_announced`, `section_not_announced`, `below_bar`), the floors (`below_floor`, `machine_five`), the source rule (`story_not_reviewed`), the review policy (`no_delivery`), or `would_announce`. It reads the rules and writes nothing. A channel with its own rules (an email list's section rule) adds itself to `CHANNEL_RULES` when it is built. It is a command and an agents' tool; the console does not offer it.
- **The door.** `announcementsRead` (`amplify/functions/image-service/schema.ts`, served by the image service function like `guidelinesRead`) runs `announcements_where` and `announcements_recent` for editors and admins and refuses everything else: reads only, and what changes an announcement stays on the command line and in the agents' tools. The function carries no PyYAML, so the read side of the relations is `link_reads.py` and the writer (`links.py`, which needs the relation types) is imported only when a link is written; a spec loads the read path with PyYAML blocked. No table, no model, no index and no resource was added; the schema gains one query field on the existing function and data source.
- **Specs:** `announcement-list-lines.feature`, `announcement-list-marks.feature`, `announcement-explain.feature` (behave), `newsroom-story-announcements.feature` and the list scenarios of `newsroom-announcements.feature` (cucumber, on the local preview's seeded data).

## Editing window, versions, pinned edits, candidates and the lock (PPY-e8ec54)

A Delivery is a draft with an edit window, not a one-shot: the machine drafts, people edit, and every edit is a new saved version. Code: `delivery_text.py` (versions, blocks and pins, pure), `delivery_versions.py` (saves, candidates, pinned blocks), `delivery_lock.py` (the lock and the unlock), `edit_windows.py` (the window lengths), `delivery_timers.py` (the timers), and `edit_handlers.py` (the operations).

- **The window is data.** It runs from the Delivery's creation to `releaseAt`, and `lockAt` comes `lockLeadMinutes` before that. Both lengths are the `editWindows` list of the announcement settings (`papyrus announcements settings set --input-file`, one entry for each kind and channel, `kind` and `channel` each optional, the narrowest entry that fits wins; `edit_windows.validate` refuses a lead longer than its window and two entries for one scope). `edit_windows.apply` gives each channel's plan its release and lock times when an Announcement is made (the announce agent applies it to every Delivery it builds, a story post and a later-added X Delivery and a roundup issue alike, from the announcement settings it reads at the start of the wake): the release is now plus the window, unless the Announcement has its own (a roundup's scheduled time), and the lock is the lead before it. Where no entry fits, the Delivery is released as soon as it is allowed and has no separate lock; nothing in the code names a length.
- **Every edit is a new version, in S3.** The words of version `n` are the file `v<n>` (a ModelAttachment of the Delivery; a file is written once and never overwritten). The row holds `version` (the newest), `textKey` and `contentHash` (the newest's) and `versions`, a log: for each version its file, key and hash, who saved it (`by`, `owner` human or machine), when, which version it `replaces` and the flags of its blocks. The catalog never holds words (`require_catalog_only`). A save with the words already there makes no version.
- **A save names the version it replaces** (`replaces`). When the Delivery is no longer there, the save is refused as `stale_version` (`StaleVersion`), and the answer names the version that replaced the one that was read, who saved it and when; two saves against one version leave one winner. A machine redraft (`Versions.redraft`) in that position, or against a lock or an open attempt, is dropped: nothing is written and the answer says `dropped`, because the person's version is newer. The row is written first, conditional on its `revision`, and the words second, so only the writer that won ever writes a file, and a save whose file never reached S3 is finished by the same call made again.
- **Pinned human edits.** A text is blocks (paragraphs). A block a person changed is `owner: human, pinned`; a block they only moved keeps what it was. A machine redraft is laid over the current version (`delivery_text.merge_redraft`): every pinned block comes out word for word, at the place the redraft gave it when the redraft reproduced it, else in place of the redraft's block at its position, else inserted. Only a person changes or unpins a pinned block (`announcements_pinned_change`; an agent is `blocked`), and an ordinary person's save may rewrite one.
- **Candidates.** `announcements_draft --candidate` keeps another text or picture beside the draft (file `c<n>`, a line in `candidates`). It changes nothing that goes out, so the lock does not refuse it. `announcements_candidate_choose` saves a new version with the candidate's words and picture (`chosenFrom` on the version), names the version it replaces like any save, and the other candidates stay (`kept`).
- **The lock is a fact.** `lockedAt` and `lockedVersion` are on the Delivery; nothing is held and nothing expires. The version locked is the version sent (`Deliveries.sendable`; the attempt log records it as `version`, and a later, preferred version never goes in that attempt). At `lockAt` (`delivery_lock.lock_at_time`): under `none` the policy-approved version is locked; under `soft` a person's approval of the current version is locked and, with nobody acting, **the engine approves the current version as the policy (`approvedBy` `system`, `approvalPolicy` says whose, the history line says why) and locks it in one conditional write**; under `hard` with no approval nothing is locked or sent, the Delivery stays due (Overdue in the list) and one flag is raised, once. A Delivery whose lock time came without a run (a late timer) is locked by the write that opens its attempt (`Attempts.open`), so the sender reads only a locked version. A change to the Story lifts a lock on words it has outgrown (`next_version`).
- **A late edit after the lock is refused** (`locked`) until a person unlocks the Delivery (`papyrus announcements unlock DELIVERY [--lock-at T] [--release-at T]`; an agent is told `human_required`). Unlocking is an event: it clears `lockedAt` and `lockedVersion`, names the new lock time (by default the release time, which must still be ahead), keeps the version that was approved approved, and the next edit makes an unapproved version.
- **An edit while an attempt is open does not change that attempt.** A person's save is the next version, flagged `preferred` and named in `preferredVersion`; the attempt sends the locked version. It is never sent here: a person teaches from it ([announcement learning](announcement-learning.md)). A machine's redraft is dropped.
- **Timers.** `Deliveries(client, files, timers)` calls `DeliveryTimers.sync(row)` wherever it writes `dueAt` (the earliest of release, lock and next attempt), so the lock and the release times are follow-up timers ([follow-up timers](follow-up-timers.md)); a fired time raises one wake for the owner `deliver`, and `delivery_lock.on_wake` re-reads the row, checks the wake still names `dueAt` and only then locks. The signed-in command line holds no scheduler rights, so a person's `unlock` writes the new `lockAt` and the deliver runtime's own writes move the timer; see "Not in this slice".
- **Operations** (one table, so newsroom and command line get them together): `announcements_versions` (read), `announcements_draft`, `announcements_candidate_choose`, `announcements_pinned_change`, `announcements_unlock`, `announcements_example` (a person says how far an edit reaches), `announcements_preferred` (how a sent Delivery should have read; never sent): [announcement learning](announcement-learning.md). A `stale_version` answer carries `replacedBy` and `head`; `locked` carries the lock.
- **Specs:** `delivery-edit-window.feature`, `delivery-pinned-human-edits.feature`, `delivery-candidate-versions.feature`, `delivery-lock-and-unlock.feature`, `delivery-nothing-unseen-is-sent.feature`, `delivery-edit-operations.feature`; `delivery_editing_test.py`.

## Relation types

`announces` runs from an Announcement to a Story and names the version looked at; `supersedes` runs from a Delivery to the Delivery it corrects. Both are in `papyrus-semantic-relation-types.yml`.

## In a pod (PPY-e78134)

A pod keeps the same two records as notes with the same field names: an Announcement note (`type: papyrus:Announcement`: `kind`, `state`, `releaseAt`, and `announces` links to the Stories) and a Delivery note (`type: papyrus:Delivery`: `announcement`, `channel`, `account`, `mode`, `state`, `resultUrl`, `attempts`, and `supersedes` to the Delivery it corrects). The words of a Delivery are the body of its note, exactly as posted. Code: `src/papyrus/pod/` (`profile.py`, `check.py`, `attempts.py`, `pages.py`, `announcement_notes.py`) and `src/papyrus_content/announcements/pod_history.py`; specs `features_backend/pod-announcement-delivery-notes.feature`.

- **Records of what happened.** A Delivery note's state is `sent`, `failed`, `withdrawn` or `superseded`; an Announcement note's is `released`, `cancelled` or `withdrawn`. `sent` and `failed` say how the last attempt ended. A pod holds nothing that is waiting to go.
- **Manual mode only.** `mode: manual` is the one value `papyrus pod check` accepts. Sending automatically needs a connected account, a budget guard and Caducus, which a newsroom has and a pod does not; a pod gets no local stand-in.
- **Attempts only grow.** `attempts` is a list of one-line entries, `<number> <time in UTC> sent|refused [by <name> | <code>]`. `papyrus pod check` fails when an earlier line differs from the last commit (changed, moved or removed), as it does for an id.
- **One live Delivery for each Announcement, channel and account.** A second is a correction: it `supersedes` the first, and the first says `state: superseded`.
- **Never a page.** The body is outside the graph, a note of either type carries none of `stage`, `draft`, `format`, `redirects` or `section`, and `papyrus.pod.pages` never lists one as a page.
- **A load is history and sends nothing.** `PodHistory.load` writes the same Announcement, Delivery and `announces` and `supersedes` relation rows, once (the key is `pod:<the note's id>`; a second load finds the first and a record the newsroom has changed is not overwritten). It has no channel and no worker, a loaded Delivery waits for no time so the due index never holds it, and its approval is `hard` with no approved version, recorded as a claim made in a pod. `papyrus.pod.announcement_notes.read` refuses a pod that does not pass the check. The command that calls it is `papyrus pod load` (not yet built); Stories are loaded first, so the `announces` links name the newsroom's own Story versions.
- **Vocabulary.** `announces` and `supersedes` are pod relation types, and `cites` and `authored_by` take a Story as their subject (a Story cites a source and names its author with plain keys). Profile version 3; a pod's `papyrus.context.jsonld` is regenerated with `papyrus pod init` into an empty folder and copied over.

## Manual mode (PPY-4410fc)

`mode: manual` is a field on the Delivery, for what has no API or no budget. Papyrus drafts and checks the words (the same draft and check path; a draft whose checks fail is blocked), a person posts them elsewhere and records the address, and the Delivery is `sent` with that person's name in its attempt log.

- **Record it.** `papyrus announcements record-manual DELIVERY --url URL` (operation `announcements_record_manual`; code `Attempts.record_manual`). One conditional write holds the attempt (`outcome: sent`, `by` the signed-in person, `url`), the state `sent` and `resultUrl`. The attempt has no event id: there is no provider event.
- **Refused:** an address that is not an http or https URL; a Delivery that is not manual, not `ready` (drafted, blocked, superseded) or already `sent` (an earlier record never changes, so recording twice is refused); a missing or changed words file; a caller that is not a person (an agent is told `human_required`).
- **Never sent automatically.** `Deliveries.releasable` answers no for a manual Delivery, `Attempts.open` and `Attempts.hand_over` refuse it (`ManualDelivery`), so no `AccountWorker` or channel ever picks it up.
- Specs: `features_backend/delivery-manual-mode.feature`.

## Correcting from the command line (PPY-3e0a8a)

`papyrus announcements correct DELIVERY --text TEXT` (operation `announcements_correct`; code `announcements/corrections.py`, handler `review_handlers.correct`) is the one door to `Deliveries.supersede` for a person or an agent at `prepare`.

- **The words are checked first.** An X Delivery's text goes through `drafting.check_draft` against the Announcement's Story (length, markup, the facts); any failure is `checks_failed`, lists every problem and writes nothing. A Delivery on another channel has the record's own rule (the words are not empty). The new Delivery records the checks that passed.
- **The new Delivery is the old one's next generation:** same channel, account, mode, audience and picture, under the review value the old one had (`approval`, `approvalPolicy`), so it goes only as that review says. The old one becomes `superseded`.
- **Refused as `constraint_conflict`, in the sentence the record raises:** a Delivery that never went (`NotSent`), one with an open attempt (`OpenAttempt`), a different correction that already exists (`CorrectedDifferently`), and one that already has another successor (`AlreadySuperseded`: a second live Delivery is never made). The same words again finish a half-written correction.
- **Writes by default**; `--dry-run` checks the input and stops before the handler. A check needs `SITE_ORIGIN` and a model for the fact check.
- **The old X post.** The words of an X Delivery are the post exactly as it will go, so the corrected Delivery's words are the checked text, a blank line and the Story's tagged link (`corrections.words`). Where the site's own X channel makes the correction, the old post is deleted as part of it (`withdrawals.Withdrawals.delete_superseded`), and the deletion cost is written on the old Delivery; the signed-in command line holds no rights on Caducus, so there the deliver side deletes it just before it sends the corrected Delivery. See "X on the records" below.
- Specs: `features_backend/announcements-correct-cli.feature`; `src/papyrus_content/announcements/corrections_test.py`.

## X on the records (PPY-efd06c)

X is one channel of an Announcement, not a row shape of its own; the old X model, its index `announcementsByAccountAndCreatedAt` and the round suffix are deleted in this change, the settings, the account connection and the spend counter are unchanged ([announcements](announcements.md)). Code: `x_announce.py` (eligibility, the draft, the dry run, the blocked draft), `x_channel.py` (Caducus's `x` channel as the attempt log's transport), `x_runner.py` (the deliver side: pause, budget, the one worker), `withdrawals.py`, `spend.py`, and the X part of the announce agent's wake (`list_cadence/story_wake.py`, `announce.py`).

- **Created with the Announcement, or added to it.** The X Delivery is written in the same `Announcements.announce` call as the Announcement and the Story's other Deliveries. A later rating that reaches the X bar makes the same call again with the same once-only key: the Announcement and the other Deliveries are found, and the X Delivery is added with an edit window counted from then. A publish that qualifies on no channel leaves no row.
- **The channel's rules, and the floors under them** (`x_announce.prepare`; `papyrus announcements explain` says the same codes): off, the channel's own rules (`eligibility.refusal`), the floors (`below_floor`, `machine_five`), a connected account (`no_account`), the source rule, and the review policy's rung (`no_delivery`). Nothing under three stars qualifies under any setting, unrated and predicted never do, and a machine never supplies the five.
- **A Delivery is drafted once.** The words are the post as it goes (the draft, a blank line, the tagged link). A Story whose Announcement already has an X Delivery is not drafted for again.
- **A blocked draft asks once.** A draft that fails a check is a Delivery that is `blocked` with `check failed` (its words, even failing ones, are kept for the editor) and one flag for the Announcement (`blocked_drafts.block_and_flag`). The checks record the inputs the draft was written under (the Story's version and a fingerprint of the guidelines). `x_announce.revisit` drafts it again only when one of them changed, once; a draft that still fails records the new inputs and is not tried again until they change again. A crash between the Delivery and its block is finished by the next wake (`x_announce.finish`). A guidelines change has no wake of its own yet: the change is noticed the next time the agent wakes for the Story.
- **Dry run** builds, checks and records the Delivery, then marks it `dry_run` with cost `0` (`Deliveries.mark_dry_run`): final, with no pending time, never due and never handed to a channel. `XRunner` also refuses to send unless the mode is On.
- **The guards are Caducus's.** `guard.SpendGuard` is asked before every post and told every charge; a refusal closes the attempt `refused` (`paused` or `budget reached`, the latter naming the time the cycle ends) and the Delivery is `blocked`. A budget refusal pauses announcements with the reason and tells the editors; `x_runner.resume_blocked` puts the held Deliveries back to ready, due now, when the guard lifts (a resume, a raised budget, a new cycle). A site whose account needs connecting again, or that has no budget or billing day, sends nothing and says so.
- **Withdraw** (`announcements_withdraw`, `withdrawals.Withdrawals.withdraw`): a Delivery that has not gone becomes `withdrawn` and nothing public changes; a post on X is deleted through Caducus and the Delivery keeps who withdrew it (its history) and what the post cost in all; a sent email or a post made by hand is refused (`CannotTakeBack`) and stays `sent`; an attempt with no answer is settled first; a superseded Delivery is not withdrawn on its own. When every live Delivery of an Announcement is withdrawn the Announcement is `withdrawn` (`cancelled` when none had gone). A person always may. An agent may only when every Story the Announcement is about was retired, otherwise `human_required`; the operation table gives it the `prepare` rung and the handler adds the "only when". The signed-in command line holds no rights on Caducus: it can withdraw what never went and says `service_unavailable` for a post that went.
- **Specs:** `announcements-x-rules.feature`, `announcements-x-drafting.feature`, `announcements-x-dry-run-and-sending.feature`, `announcements-x-budget-and-pause.feature`, `announcements-x-model.feature`, `announcements-withdraw.feature`, `announcements-correction-deletes-old-post.feature`, `announce-edit-windows.feature`.

## Not in this slice

The Caducus `x` channel release and the queue with one consumer for each account (X is off everywhere until both exist and the owner turns it on), the buttons that act on a line (release, stop, correct; the command line's `correct` and the editing operations are built), the console's editing surface, and the channel checks of a person's edited words (a save records no checks; the drafter's checks run on a draft). The signed-in lane cannot move a Delivery's follow-up timer (it has no scheduler rights), so a timer for a lock time that a person's `unlock` just moved is set by the deliver runtime when it next writes the row; until it is deployed, the Overdue mark in the list is what shows a lock that nothing woke. Nothing sends.
