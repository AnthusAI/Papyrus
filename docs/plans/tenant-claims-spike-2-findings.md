# Auth spike part 2 findings (PPY-f4d892, parent PPY-9f3de0)

Status: **static evidence only; runtime scenarios not yet run.** The agent was refused permission to run `ampx sandbox` (deploying to AWS), so nothing below was observed against AppSync. Sources: the AppSync resolver templates Amplify Gen 2 (`@aws-amplify/backend` 1.x) generates for `spikes/tenant-claims-2` (synthesised offline with `CDK_OUTDIR`), the installed `@aws-amplify/api-graphql` 4.10.2 source, and AWS documentation. To finish: `cd spikes/tenant-claims-2 && npm i && . ./.env.spike && AWS_PROFILE=legacy npm run sandbox && npx ampx generate outputs --stack <stack> --format json --out-dir . && npm run spike`, then `npm run sandbox:delete`. Users are created without any password (no invite) and sign in through a sandbox-only CUSTOM_AUTH challenge, because Papyrus uses Google sign-in only and a Google round trip cannot be scripted.

| Question | Answer | Evidence |
|---|---|---|
| Do index lists through a GSI keyed `<tenant>#...` return full pages? | **Yes, if the partition is tenant-pure.** The list resolver's only protection is a post-filter `or[{tenantId eq <claim>}]` on the DynamoDB query. A tenant-prefixed key keeps every row in the partition the caller's own, so the filter removes nothing and pages are full. An index key shared across tenants (for example `status = published`) returns short or empty pages. A caller querying another tenant's prefix gets zero rows (filtered), not an error. | generated `listReference*` auth function; runtime page sizes to be measured by `run-spike.ts` |
| Subscriptions filtered per tenant or off? | **Filtered, no need to turn them off.** The subscribe-time auth step adds a server-side filter `tenantId eq <claim>` (or-ed over the role claims) and rejects a `tenantId` argument that differs from the claim. The filter is fixed at subscribe time from the token, so a switch of tenant needs a new token and a new subscription. | generated `onCreateReference` auth function |
| Can `tenantId` be made immutable? | **Yes with a field-level rule, no without.** With model-level owner rules only, update authorisation checks the stored row's owner, never the new input, so an editor can move a row to another tenant (Amplify itself warns: "owners may reassign ownership ... Item: [tenantId]"). Field rules granting `create` and `read` but not `update` make the update resolver list `tenantId` as a denied field ("Unauthorized on [tenantId]"). The tenant index key (`tenantKey`) needs the same lock, otherwise an editor can move a row into another tenant's index partition. Create with a foreign `tenantId` is denied; create without one defaults to the caller's claim. | generated `Item` and `Reference` update/create templates |
| Which token does the Amplify v6 data client send? | **The access token**, for HTTP and for websocket subscriptions (`graphqlAuth.mjs`, `authHeaders.mjs`: `tokens.accessToken`). Claims must therefore be in the access token. | `@aws-amplify/api-graphql` 4.10.2 |
| Does customising its claims need Cognito Essentials? | **Yes.** Access-token customisation needs the pre-token-generation trigger event version 2 (`V2_0`), available on the Essentials and Plus feature plans (Lite only for older pools with Advanced security). Version 1 changes the ID token only. Amplify Gen 2's `triggers.preTokenGeneration` wires V1, so the spike sets `PreTokenGenerationConfig` / `LambdaVersion: V2_0` and `UserPoolTier: ESSENTIALS` by CDK override. Price: Essentials $0.015 per monthly active user above 10,000 free; Lite about $0.0055 (tiered, so Essentials costs more); Plus $0.020. Social and OIDC sign-ins (Google) are billed as direct MAU on the pricing page; the $0.015 federation line applies to SAML/OIDC at a 50-MAU free tier. | AWS Cognito pricing and pre-token-generation docs, 2026-11-10 |

## Design consequences to record in the design note

1. `clientMetadata` (the way the spike tells the Lambda which tenant the session acts for) reaches the trigger only from `RespondToAuthChallenge` / `AdminRespondToAuthChallenge`, **not** from `InitiateAuth`, and is absent on hosted-UI and refresh-token invocations (`TokenGeneration_HostedAuth`, `_RefreshTokens`). With Google sign-in the active tenant must therefore be stored server-side (for example a "current site" on the person's membership row, written before the token is issued or refreshed) and read by the Lambda; the Lambda cannot take it from the request.
2. Every tenant model needs a field-level lock on `tenantId` and on any field that is part of a tenant-prefixed key.
3. Every index on a tenant model must have a tenant-prefixed partition key; the generated suite (PPY-65e5a9) should fail on an index whose key is not prefixed.
4. The post-filter on lists means a tenant-prefix mistake leaks nothing but also pages badly; it is a correctness and cost issue, not a leak.
