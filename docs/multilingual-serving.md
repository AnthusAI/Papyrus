# Serving a site in several languages

Status: built in the engine (initiative PPY-82f150, epic PPY-756495); no site serves a second language yet. How a translation is published, and what holds it back: [the translation procedure](story-translation-procedure.md#publishing-a-translation). Plan: [docs/plans/multilingual-publishing.md](plans/multilingual-publishing.md). Specifications: `features_backend/language-serving.feature`, `features_backend/language-serving-settings.feature`, `features_backend/item-language.feature`.

A translation of a Story is a sibling Story (its lineage is `{primaryLineageId}--{language}`) joined to the original by its language group (`Item.language`, `Item.languageGroupId`, PPY-843a7c). This page covers what happens once such a localization is published: where it is served, what its page says about the other languages, and what each language's listings, sitemaps and links contain.

## Deploying the release that adds languages

The post-deploy render (`reprojectOnDeploy`) writes the language fields on every row written before them, first, before the editorial policies or the render read anything (`ensure_item_languages` in `src/papyrus_content/item_language_backfill.py`): the site's primary language (`en` when the site never set one) and each Story's own lineage as its group, on `Item` rows (read through the version-state index) and `PublishedItem` rows (one point read per lineage, by id), only where missing, keeping each row's own update time. A clean run leaves `_papyrus/migrations/item-languages.json` in the site store, so a later deploy reads that one object and writes nothing. A run that fails part-way fails the deploy before the render (CloudFormation rolls the backend back to the previous release, which does not read languages) and leaves no marker; the next deploy finishes it. `papyrus stories languages` is the same code run by hand. Specification: `features_backend/deploy-item-languages.feature`.

Every writer after that sets the fields itself. All of them (`papyrus stories save-version`, the console's saves, the agent and ops procedures, `stories create`, the checklist's step rows, imports) write Items through the authoring client, whose `create_record` and `upsert` call one helper, `with_item_language` (`src/papyrus_content/item_language.py`): the language and group as written, else those of the version it follows (`previousVersionId`, or the row it replaces), else the site's primary language (the `languages` setting's `primary`) with the Story's own lineage as its group. A translation sibling keeps its own language because the localization procedure names it. A row without a language therefore means a writer older than 5.110.0 (the release that added the helper) wrote it, for example a CLI still pinned to 5.109.0; the refusal at publish, projection and `editorial check-version` says so. `papyrus stories languages` repairs the rows, and the writer has to be upgraded to stop new ones. Specification: `features_backend/item-language.feature`.

## The setting

There is one languages setting: the editorial check settings' `languages` (Administration > Editorial checks, stored in `EditorialCheckSettings`). `primary` and `enabled` say which languages the site writes in ([editorial checks](editorial-checks.md)). Three more keys say how they are served, and a fourth (`auto`) whether translations are made on publish (`src/papyrus_content/language_serving.py`):

```json
{"languages": {
  "primary": "en",
  "enabled": ["en", "es-419", "zh-Hans"],
  "prefixes": {"es-419": "es", "zh-Hans": "zh"},
  "public": ["en", "es-419"],
  "slugs": {"es-419": "translated", "zh-Hans": "characters"}
}}
```

| Key | Meaning | Default |
| --- | --- | --- |
| `prefixes` | URL prefix of each enabled language other than the primary: a lowercase path segment (`es`, `zh`, `zh-hant`). Paths use the prefix; `<html lang>`, `hreflang`, `og:locale` and JSON-LD `inLanguage` use the tag. | the tag's base subtag, lowercased (`es-419` to `es`, `zh-Hans` to `zh`) |
| `public` | Languages the public site serves; the primary is always one. An enabled language that is not public is written, translated and checked, but its published localizations get no page (the plan's "preview" state). | only the primary |
| `auto` | `{"enabled": true, "automation": "SITE.story-localize", "publish": true}`: translate every Story into every enabled language when it is published or republished, on the site's runner, and publish the translations a run saved cleanly (`publish`, default true). The Automation runs the registered translation procedure. Set with `papyrus editorial languages --auto on --auto-automation ID [--auto-publish off]`. [Translating on publish](story-translation-procedure.md#translating-on-publish). | off |
| `segments` | The path segments of an edition's sections, types and authored pages in the language: `{"es-419": {"articles": "articulos", "concepts": "conceptos", "security": "privacidad-y-seguridad"}, "zh-Hans": {"articles": "文章"}}`. The key is the segment as the English site writes it (the Concepts are `concepts` in every edition); a segment not listed keeps its English form; a nested page path (`security/videos`) is translated one segment at a time. A value is lowercase letters, digits, hyphens and underscores in any script, one NFC form, unique within its language; two top-level paths of an edition may not end up at one address, and no Story served at the edition's root may have a translated segment as its slug. Set with `papyrus editorial languages --set-segment es-419:articles=articulos` (`TAG:SEGMENT=` clears one). | none |
| `slugs` | How a localization's slug is drafted at its first publish: `translated` (the translated title in plain letters), `characters` (the title in its own script; Chinese characters kept), `pinyin` (the title romanized by a romanizer the caller supplies), `primary` (the original's slug). | `characters` for a language Humanus counts in characters (Chinese), `translated` for every other |

A setting that breaks a rule is refused with a message naming it when the projection reads it (a refusal stops every projection until it is corrected, so the console and the CLI check a change before saving it; see below): a prefix two languages share, a public or slug language the site does not write in, a public list without the primary, an unknown slug policy. The projection reads the setting once per run (one record read).

**Setting it.** Two supported controls change these keys, and both are checked by the same function, `serving_languages`, before anything is saved:

- *The console.* Administration > Editorial checks > Settings shows, for each enabled language other than the primary, whether it is public (readers can visit its pages), its web address prefix (the default is shown and used when the box is empty) and how its page addresses are made (the default is shown). The primary is always public and has no prefix. A language that is enabled but not public is written, translated and checked but gets no page. The form asks the `describeEditorialLanguages` query (an editor-or-admin read that touches no data: it runs `describe_serving` in `language_serving.py`) as the admin edits and shows its message, for example that two languages would both be served under `/es/`; the save button stays off until the setting is accepted, and a save asks once more. Taking a language out of "Languages the site writes in" takes its public flag, prefix and slug policy with it. A save writes the `languages` object as the form holds it, so every key the form does not show is kept as stored.
- *The CLI.* `papyrus editorial languages --enable es-419` (or `--disable`) is how a site starts or stops writing in a language: the tag is checked against the languages the installed Humanus has a pack for (`en`, `es`, `es-419`, `zh-Hans`; `zh-CN` is stored as `zh-Hans`), added to `languages.enabled` and never made public, and the language's starter policy packs are imported (`DEFAULT_STARTER_PACKS`). It prints what it did and the commands to run next (the writing and glossary overlays, a register choice, a dry-run translation, going public). `--dry-run` prints the same and writes nothing; running it again changes nothing. `--disable` is refused for the primary language and for a language that has translations, and takes the language's public flag, prefix, slug policy and segments with it; its policies stay. `papyrus editorial languages` lists each language's public state, prefix and slug policy, marking the defaults. `--set-public es-419` makes the listed languages public (the primary is added; an empty list leaves only the primary), `--set-prefix es-419=es` and `--set-slug es-419=primary` set one language's value (repeat the flag for more; `TAG=` returns a language to its default). It writes unless `--dry-run`, changes only the keys it names, and refuses what the projection would refuse before it writes. Admins only, like the console's save.

Specification: `features_backend/editorial-languages-setting.feature` (the rules and the CLI), `features_backend/editorial-languages-enable.feature` (enabling and disabling a language), `features/newsroom-editorial-languages-admin.feature` (the console form).

**Translated path segments.** With a `segments` table an edition serves `/es/articulos/el-sonido/` and `/zh/文章/…/` instead of `/es/articles/…`. Every listing, Story page, feed, sitemap entry, `hreflang`, canonical, switcher alternate, navigation link and Markdown twin uses the translated path (non-ASCII segments percent-encoded in every URL, NFC in object keys, as for Chinese slugs). English keeps its addresses, and `/wiki/` and `/es/conceptos/` are each other's alternates. Every address an edition served with the English segment redirects permanently to the translated one with the same path: the edition writes one exact redirect per listing, paged listing, feed, Markdown twin and Story page into the site's redirect store (a Story page's old address also through the item's former page keys), and the edge function keeps the request's query string on every redirect it answers. A redirect source is limited by the store's 512-byte keys (see Unicode addresses). A later change of a translated segment redirects the Story pages through their former keys; the listings of the old translated segment are not redirected (the table keeps no history yet).

**Changing the segments table (the safe order).** The table is data in the editorial check settings, and an edition changes address only when it is next projected. Do it in this order, once, with nothing else projecting:
1. Pause anything that publishes translations (a projection of one Story while the full render runs doubles the work and the render holds a lease).
2. `papyrus editorial languages --set-segment TAG:SEGMENT=value ... --dry-run`, read the table it prints, then run it again without `--dry-run`. Nothing is served differently yet.
3. Re-render the site once: `papyrus ops content rerender --all --no-invalidate`. The CLI call can time out (exit 5) on a site this size: that is not a failure, follow the job with the same command plus `--status` and never start a second one while it says running. Do not purge the whole site: a full invalidation is thousands of paths; the new pages are new keys and the sitemap and feeds are refreshed by the render.
4. Wait for the redirect rules: request an old listing address with a query string (`/es/articles/?utm=1`) and expect a `301` to the new address with the query kept. The render writes the redirects after the pages (thousands of keys, 50 per call), so on a large site this is minutes after the pages are live.
5. Verify the old addresses of Story pages, listings, feeds and the `.md` twin, the switcher in both directions, `hreflang` and the sitemap, and only then announce the new addresses.

A render deletes the pages of the old layout. Before the fix that ships with this section, it did that before it wrote the redirect rules, so on Machines on Machines (2026-11-15) every old Story address was a 404 for about 20 minutes while the redirect rules were still being written. The projection now writes the redirects first and removes the pages that an old address pointed at last (the full render and a single Story's projection), so a page is never gone before its address redirects; the redirect keys are still written in a batch after the new pages, so an old address can answer with its old page for a while, never with a 404 (`features_backend/language-path-segments.feature`, the scenario "A page whose address moved is removed only once its old address redirects").

Only the "primary at root" URL mode exists: the primary language keeps every address it has; each other language lives under its prefix with the same structure (`/es/articles/{slug}/`). The "language prefixed" mode for new sites is not built.

## Editions

The standard front end projects a site that serves more than one language as one edition per public language (`src/papyrus_content/projection/standard/editions.py`). The primary edition is the site as it always was. Every other edition is the same front end over that language's published Stories only, with its pages under `/<prefix>/` and the words of its settings taken from the language's interface strings.

| An edition renders | An edition does not render (their words are the primary's) |
| --- | --- |
| the language's Story pages; its home and section listings, with paging and archives; its RSS and Atom feeds (`/es/feed.xml`); its sitemap (`/es/sitemap-0.xml`) | authored pages, collections, tag pages, the showcase, Reference grids and section front pages, plugin pages, forms, page actions, `llms.txt`, Markdown twins of listings, a 404 of its own |

**Every public language has every index the site has, from its first day.** A language's home and the listing of every section the primary language lists exist in each edition whether or not a Story has been translated into them yet (`/es/articles/` is never a 404 and never a dead end of the navigation). Until it lists a Story, such a page says so in its language and links to the same page in the primary language (`page.untranslated`, `components.untranslated_notice`; the strings `listing.untranslated` with `{original}`, and `listing.untranslatedOriginal` for the link's words), is `noindex`, is left out of the language's sitemap, and is left out of the `hreflang` links of its counterparts (a search engine is never pointed at a page it may not index); the language switcher still offers it, because a reader who chose the language wants to land in it. The first Story published into the listing makes it indexed, drops the notice and adds it to the `hreflang` sets, as the engine re-renders the counterparts (the listing's input digest includes each alternate's `indexed` state). A language with no Story at all has no sitemap file, since every page of it is `noindex`. A localization is served only while its original is published: its group facts (section, references, stars) are the original's. An edition therefore ranks its Stories as the primary language does (`page.ranked`, the listings and the home): a translation takes its original's stars and its original's publication date (its bucket, and the date its card shows unless it has a date of its own), so the lead and the order of `/es/` are those of `/` among the Stories that have been translated (`features_backend/language-edition-ranking.feature`).

Concepts: a language edition serves the site's wiki pages under `/<prefix>/concepts/` (Ryan, 2026-11-13: "Concepts" is the public term). The primary language keeps its address (`/wiki/` on the sites that have one), because published URLs are never moved; the English `/wiki/` and the Spanish `/es/concepts/` pages of one Concept are each other's `hreflang` alternates. The Concepts group is the type group of a wiki type, or the section the wiki sync files pages under (`wiki`).

A translation is read from the CMS only while its original is published (`served` and `PublishedContentSource.published_row` in `projection/source.py`): a published row whose language group is another lineage than its own, with no published row for that group, is left out of the site index, so every page, listing, feed, sitemap entry and alternate that the projection derives leaves with the original. Publishing or taking down a Story projects its published translations again (`engine._project_translations`: one point read each), which writes or removes their pages; no record is changed.

So an English listing, feed or sitemap never lists a translation, and a Spanish one lists only Spanish Stories. The static projection needs no new index for this: it already reads every published summary once per run (`list_published_item_summaries`), and each summary carries `language` and `languageGroupId` (copied onto `PublishedItem` at publish; no index on them).

The CMS's own listing keys (`typeStatus`, `sectionStatus`, `headStageKey`, read by the console, the reader app and the newsroom commands) do not carry the language yet; that is the plan's "listing keys carry the language" change, filed as PPY-f33254 (see [Not built yet](#not-built-yet)).

## Authored pages in an edition

An authored page (`pages` in `projection.json`) is the primary language's only, unless it sets `"languages": "localize"`. A page that opts in is rendered under the prefix of each public language that has the page's file in that language: `pages/findings.md` is `pages/findings.es-419.md` in es-419 (`localized_source` in `editions.py`). Its title and description come from the interface strings `page.<id>.title` and `page.<id>.description` (required for a language that has the file), its includes are evaluated over the edition (`listing` over the language's Stories; `references` and `threads` read the site's one snapshot, which every edition shares; thread links go to the primary language's thread pages, a link that leaves the language), and it is an alternate of the same page in every other language that renders it (`hreflang`, `page.alternates`, `page.link_map`, the sitemap). A language without the file does not render the page and is not one of its alternates, so a site's navigation can link to the localized page exactly when it appears in `page.link_map`. Specification: `features_backend/language-authored-pages.feature`. Plan, and what is not built yet (translated path segments, per-language 404 and listing Markdown twins, the translation procedure for pages): [docs/plans/edition-authored-pages.md](plans/edition-authored-pages.md).

## An edition's 404 and Markdown twins

An edition writes the Markdown twin of its home and of every listing it advertises (`/es/index.md`, `/es/articles/index.md`), as the primary language does. An edition whose interface strings have all of `notFound.title`, `notFound.heading`, `notFound.text` and `notFound.back` also writes its own `/<prefix>/404.html` in the language, with the edition's chrome, `noindex`; a language without the four keys has none. Serving it is the edge's part: the origin-response function of `infra/edge/s3-projection-cms.yaml` fetches `/<prefix>/404.html` for a miss whose first path segment is one of the stack's `LanguagePrefixes` parameter (comma separated, the site's `languages.prefixes`, baked into the function with `Fn::Sub`), falls back to `/404.html` when that language has no page, and fetches `/404.html` for every other miss (`scripts/test-edge-language-404.mjs`). Edge stacks are hand-run today (`infra/pipeline/README.md`, "What does not fit"), so the parameter takes effect when a person updates the stack with a change set.

## What each page says about its languages

On a site that serves more than one public language:

- `<html lang>` is the page's own language tag.
- The head lists `<link rel="alternate" hreflang>` for each public language the page is published in, itself included, then `x-default` (the primary language's page). A page that exists in one language only lists none. The `hreflang` value is the tag without a UN M.49 region (`es-419` is `es`; `zh-Hans`, `pt-BR` stay), because search engines refuse a numeric region (`hreflang_value` in `projection/standard/editions.py`, also `page.alternates[i]["hreflang"]` for a site's switcher and the links core draws); `<html lang>`, `og:locale` and JSON-LD `inLanguage` keep the full tag. The sitemaps carry no `xhtml:link` entries, so they need no such value.
- `og:locale` is the page's tag with an underscore (`es_419`), with an `og:locale:alternate` for each other language; the article JSON-LD has `inLanguage`.
- Each page is canonical to itself.
- A translation's page also says what it is: the JSON-LD has `translationOfWork` (`{@type, url, inLanguage}` of the original) beside `inLanguage`, its Markdown twin adds `Language` and `Translated from` to its facts line (and `Translation: machine` for a machine translation), and the page carries a line in its own language below the byline (from the interface strings) that reads the version's translation kind (`metadata.localization.translation`). A **machine** translation says an AI translated it (`translation.label`, with the link to the original). An **imported** translation (finished copy a person wrote, `papyrus stories import-translation`) never claims AI and says nothing of its writer: its line is only the link to the original, in the words of `translation.original`, and its twin names no kind and no writer. Who made the copy is the byline's to say, from the version's `author` and `drafting` front matter (the site's byline hook reads them, so "By various bots and NAME" or "By NAME"), translated into the page's language like every byline. No JSON-LD `translator`. Spec: `features_backend/translation-notice-kind.feature`.
- The sitemap index lists one sitemap per language (`sitemap-0.xml`, `es/sitemap-0.xml`); with the `single` style every language's URLs are in the one `sitemap.xml`.

Alternates exist for Story pages (the published members of the language group), the home, and page 1 of each section listing: the edition's listing of the same section, found by the section's address in the primary language (the Concepts are `/wiki/` in English and `/concepts/` in every other language, and are each other's alternates). A home or section front page that a site writes as an authored page (`pages` with `path` equal to the listing's address, as Machines on Machines' home is) carries the same alternates, so the language switcher is on every index page and not only on the generated ones.

Publishing, renaming or taking down a localization renders the other languages of its group again (their alternates change): as many item pages as the group has languages, in the same projection (`dependent_item_ids` in the projector, `_render_dependents` in the engine), and only those. A listing page's input digest includes its alternates, so the home and section pages of each language are rendered again when a language gains or loses that page.

## What a site's hooks receive

Every `StandardPage` (see `hooks.py`) carries:

| Field | Content |
| --- | --- |
| `page.language` | the page's BCP 47 tag |
| `page.strings` | the site's interface strings in that language (`strings/<tag>.json`) |
| `page.primary_language` | the site's primary language (on a site that serves several) |
| `page.alternates` | `({tag, name, url}, ...)`: the page in every public language it exists in, itself included, primary first; `name` is the language's name in itself (`Español`, `中文`); empty when the page exists in one language |
| `page.link_map` | `{page path: {tag: page path}}` for every Story page and listing that exists in more than one language |
| `page.untranslated` | on the home or a listing of an edition that has no Story to list yet: `{tag, name, url}` of the same page in the primary language; None otherwise. Core places the notice (`components.untranslated_notice(page.strings, page.untranslated)`); a site whose hooks compose the body places the same line. |
| `page.translation` | on the item page of a translation: `{tag, name, url}` of the original it was translated from; None on every other page. Core places the line under the byline (`components.translation_notice(page.strings, page.translation)`); a site whose hooks compose the body places the same line. It is the page's data, not the Story's text. |
| `page.link_in_language(path)` | `(path, leaves_the_language)`: where a link to a page of this site goes from this page. A page that exists in this page's language is linked there; one that does not keeps its address and `leaves_the_language` is True, so the site marks the link. |

The head tags and the language switcher are core's; the translator never chooses link targets, the published language groups decide them.

**The language switcher** (`components.language_switcher`, also `page.language_switcher` for a hook that composes its own `masthead` or `page_body`) draws `page.alternates`: the Languages icon and the current language's own name (`language.name`) open a list of the page's languages, each named in itself and carrying its own `lang` and `hreflang`, the current one marked by a check mark and `aria-current`. It is on by default on every page that exists in more than one language and draws nothing on a page that exists in one. It offers an edition's listing that has no Story yet (the reader who chose the language wants to land in it), although such a page is not in `hreflang`. It is a `details` element, so Enter or Space opens it and each option is a link in the Tab order with no script; `_plugins/papyrus-language-switcher-v1.js` adds Escape (focus returns to the control) and a click outside to close it. The control's accessible name is `<switcherLabel>: <current name>`. It has no border, uses icons from Lucide only, and the current language never depends on colour. Like `site.notice` it has two settings, both data, under `site.languageSwitcher`: `placement` is `masthead` (default; in the masthead after the navigation), `footer` (a line above the footer) or `none` (no switcher: `page.language_switcher` is empty, for a site that draws its own control from `page.alternates`). A site whose hook composes its own `masthead` keeps the default and places `page.language_switcher` where it belongs; `prominence` is `normal` (a filled control) or `quiet` (the icon and the name in muted text, no fill). The brand pack's tokens colour it; a site that does not link the component stylesheet styles the `markus-language-*` classes itself. The interface strings it needs are `switcherLabel` (the word "Language") and `language.name`, in every public language including the primary; with `placement: "none"` the word is not needed.

**Words and dates in the page's language.** The skip link says the language's `skipToMain` interface string (required in every public language including the primary; a site that serves one language and writes no strings gets the engine's English). Dates the core components print (cards, bylines, the article header) are written in the language's own long date format from the CLDR data (`15 de noviembre de 2026` for `es-419`, `2026年11月15日` for `zh-Hans`) on a language edition; the primary language keeps the site's `dateFormat` (or ISO dates).

## Concepts in a language

A Story's concepts (`mentions`, `tagged_with` and `related_to` edges to Concept nodes) are written once, on the original, and every language reads them there: the projection reads a translation's concept edges through its language group (`read_site_relations`, the fourth member of each Story tuple), and `papyrus stories link-concept` run on a translation attaches the tag to the original and says so (`translationOf`). A translated Story page shows a concept chip only when that Concept has a published page in the page's language; it links there, and no chip leads out of the language. Every other relation (the sources a Story is based on, its related Stories) stays the original's, so a translation is never the page a citation links to. The concept popularity count of a language is over its own Stories. Concept names and descriptions in other languages (labels) are not stored yet: a Concept has a page in a language only when that page is a translated wiki page.

## Interface strings

A site's chrome words live in its static directory, one file per language: `strings/en.json`, `strings/es-419.json`, `strings/zh-Hans.json`, each a flat object of `key: text`. The primary language's file names every key the site's own chrome needs; hooks read them from `page.strings`.

A language is public only when its interface strings are complete (`projection/standard/interface_strings.py`). The projection refuses a public language whose file lacks a key it requires, naming the language and the keys. The required keys are every key of the primary language's file plus the ones the standard front end needs, derived from `projection.json`:

- `language.name` (also required in the primary's file);
- `site.name`: the publication's name in the language. It is data per language (Ryan, 2026-11-15: the brand is localized, "Máquinas Sobre Máquinas"). The edition uses it for the masthead and footer name, the `<title>` suffix, `og:site_name`, the structured data's publisher, the feeds' titles, Markdown twin headings and the 404; `site.shortName` (when `projection.json` sets `site.shortName`), `site.publisher` (when it sets `site.publisher`) and `feeds.title` (when it sets a feed title other than the site's name) are required the same way; so are `seo.defaultImage` and `seo.defaultImageAlt` when the site sets a default share picture (it usually carries the name, so each language has its own file). The structured data of every page lists the name in each other public language as the publisher's `alternateName` (the primary language's first), and the home carries a `WebSite` block with the same `alternateName` list, so a search engine joins the editions as one publication. Specification: `features_backend/language-site-name.feature`;
- `home.label`;
- `listing.pageSuffix` (with `{page}`);
- `site.description` and `site.tagline`, when set;
- `section.<name>.label` and, when set, `section.<name>.description`, for each section with a listing page;
- `nav.<href>.label`, for each navigation link an edition keeps (the home and section listings; other links leave the edition and are dropped);
- `notice.label` and `notice.text`, when the site has a `site.notice` (satire, AI-drafted): a language edition says the notice in its own words on its pages, its Markdown twins, its feeds' entries and its structured data (`genre`); a public language without them is refused, so the notice is never said in the primary language's words on another language's page;
- `footer.text`, when set;
- `listing.untranslated` and `listing.untranslatedOriginal`: the notice on an index with nothing translated yet. `listing.untranslated` has `{original}` where the link goes ("Todavía no hay traducciones aquí. Lee el {original}."); `listing.untranslatedOriginal` is the link's words ("índice en inglés").
- `translation.label` and `translation.original`: the line every translated page carries. `translation.label` has `{original}` where the link to the original goes ("Traducido por IA del {original}"); `translation.original` is the link's words ("original en inglés").

The strings are part of the shared fingerprint, so changing one renders the site again. The core components' own fixed words (`Skip to main content`, `Menu`, `Newer`, `Older`) are not interface strings yet, so a site whose hooks do not draw its own body and navigation would show them in English on an edition (PPY-bb4001).

## Unicode addresses

A Chinese localization has a slug in Chinese characters (`能泄露你住在哪里的声音`). One rule covers every address (`src/papyrus_content/url_paths.py`):

- An object key (S3, a local build) is the page's path as text in Unicode NFC: `zh/articles/能泄露你住在哪里的声音/index.html`. A slug is normalised to NFC when it is drafted and when its key is built, so a decomposed spelling is the same page.
- Every URL Papyrus writes is the percent-encoded form of that key (UTF-8, upper-case hex, RFC 3986 path characters left as they are): links, canonical, `og:url`, `hreflang`, sitemap `<loc>`, redirect sources and targets, and edge invalidation paths. A key in ASCII is unchanged by the encoding, so no existing address changes.
- `UrlPolicy.key_for_path` decodes a path back to its NFC key.
- An invalidation path is counted once per form a page is cached under (`/dir/` and `/dir/index.html`), encoded, against the 25-path cap.

A slug's stored form is `page_slug` (`markus_renderer/build.py`): a name whose every character folds to ASCII gets the ASCII slug exactly as before; a name in a script with no ASCII form, already a slug (lowercase letters and digits joined by single hyphens), is kept in NFC.

Drafting a slug (`localized_slug`, used by the translation procedure at a localization's first publish):

- `characters`: full-width letters and digits become ordinary ones and letters are lowercased (NFKC); every run of anything that is not a letter or digit (punctuation, full-width punctuation such as `，。「」`, symbols, spaces including the ideographic space) becomes one hyphen. `AI，会说谎吗？「真相」` becomes `ai-会说谎吗-真相`.
- There is no chosen length limit (Ryan, 2026-11-13). The one technical limit is the directory name a page is written under: 255 bytes of UTF-8 on the file systems a site is built on (85 Chinese characters). Only a longer title is cut, at a hyphen or a whole character; a stored slug longer than that is refused when its page is projected. Its percent-encoded address (at most 765 bytes for the slug) stays inside an S3 key (1,024 bytes) and CloudFront's request line (8,192 bytes). It can exceed the 512-byte key of the edge's redirect store (a CloudFront KeyValueStore), which only a retired or renamed page needs: a Chinese slug above 56 characters cannot be redirected from until the redirect store takes longer keys (a decision for Ryan).
- A title that leaves nothing (only punctuation) is refused: the localization waits for a person to give it a slug. No address is invented.
- `unique_slug` adds `-2`, `-3` and so on until no other Story of the same language has the slug.
- After the first publish the slug is fixed by the slug lock; a later change is a retire with redirect for that language only.

What the tests prove (synthetic site, fakes): the NFC key in the page writer's store; the encoded canonical, `hreflang`, sitemap entry and listing link; a decomposed slug served at the composed key; a renamed Chinese page redirected from the encoded old address to the encoded new one; encoded invalidation paths, one per cached form.

What only a real CloudFront and S3 can prove (a gated check before any Chinese page is public; no AWS was used to build this):

1. A browser request for the encoded path reaches the S3 object stored under the UTF-8 key, through the edge function's directory-index rewrite.
2. The edge function's redirect lookup matches the encoded request URI exactly (a client that sends raw UTF-8 or lower-case hex would miss the redirect).
3. CloudFront accepts the encoded invalidation paths and purges the cached page.
4. The S3 page writer's `put_object` and `head_object` with a non-ASCII key, and the redirect store's `update_keys` with an encoded key near the 512-byte limit.
5. Search engines and social previews read the encoded canonical and `hreflang` as the same page.
