# Notifications (the `notifications` plugin)

Status: Built, off everywhere (PPY-44721a, PPY-38be08, public audiences PPY-1081ad). Nothing is enabled on any site. Plan: [plans/public-audiences.md](plans/public-audiences.md). Architecture: `docs/notifications-plan.md` in AnthusAI/Caducus. There is no central service: [Caducus](https://pypi.org/project/caducus/) (`caducus[notify]`, pinned exactly in `amplify/plugins/notifications/function/requirements.txt`) runs inside each site's own stack, with the site's own table.

## What a site gets

One switch in `papyrus.config.ts`, following [plugins.md](plugins.md):

```ts
backend: {
  plugins: [{
    name: "notifications",
    siteId: "example",                       // the sending stack's SiteId; SES set papyrus-<siteId>
    siteOrigin: "https://news.example.com",
    basePath: "",                            // the site's urls.basePath
    sendingDomain: "example.com",
    fromAddress: "notifications@example.com",
    fromName: "Example News",
    theme: { accent: "#aa3300", text: "#111111", background: "#ffffff" },   // same fields as the newsletter's
    lists: [{ id: "stories", name: "New stories", rule: { sections: ["News"] }, approval: "admin" }],
    consent: "I agree to get the emails I choose from Example News and can unsubscribe at any time.",  // the form shows exactly this
    confirmWindowHours: 72,                  // optional; how long an unconfirmed address is kept and the link works
  }],
}
```

A list may also name `family` (the cadence family, below) and, for a daily or weekly list, `cadence`, `sendAt` (`{time}`, plus `day` for a weekly list) and `timeZone`, as the site's `lists` document does; the function reads them to put a reader's switch at the next period start.

`computeRoleArn` comes from `PAPYRUS_COMPUTE_ROLE_ARN` as for the newsletter. Bad settings stop the synth.

The plugin adds one stack, only where it is listed:

| Resource | Notes |
|---|---|
| Table `papyrus-notifications-<siteId>` | retained, customer-managed KMS key with rotation, TTL `expiresAt`, GSIs `byRecipient` and `byList` (a list's confirmed subscribers, keys only), no point-in-time recovery |
| SSM `/papyrus/<siteId>/notifications/recipient-key` | SecureString, created once, never overwritten |
| Functions (Python 3.12, arm64, one bundle with `papyrus_content` and Caducus) | `papyrus-notifications-<siteId>` (router), `-email-`, `-flush-`, `-ses-`, and `-pause-` (only without the newsletter plugin) |
| Queues | the email queue with a dead letter queue, and a dead letter queue for failed asynchronous router invocations; an alarm on each (no alarm action: the account's operator listener reads every alarm) |
| EventBridge rules (default bus) | every minute for the flush; SES events of the site's configuration set, only for mail tagged with this site and a delivery id; the two rate alarms entering ALARM (only without the newsletter plugin) |
| Alarms | one on each dead letter queue; without the newsletter plugin also the bounce-rate and complaint-rate alarms `papyrus-notifications-<siteId>-bounce-rate` and `-complaint-rate` (same metrics and thresholds as the newsletter's) |
| IAM | the router reads the one `getPublishedItem` AppSync field; the email function sends only from the configured address through the site's identity and set; the router may remove an address from the SES account suppression list (a reader's own opt-in after a bounce); only the CMS compute role may invoke the router (a resource policy); only the CMS compute role invokes it |

No GraphQL model or operation, so no AppSync realtime. The mail carries the site's own theme (`THEME_JSON`, rendered by `papyrus_content.email_render`, passed to Caducus as its renderer).

## The publish path

A publish tells this function nothing (PPY-e3bb2b). The best-effort call that used to invoke the router from `content-actions` with a swallowed error, `publish_alerts.announce_published`, is deleted, with the `PAPYRUS_NOTIFICATIONS_FUNCTION` variable and the invoke grant the plugin gave `content-actions` (`features_backend/announce-durable-triggers.feature`, `src/papyrus_content/publish_trigger_test.py`). "The page is live" now reaches the announce agent as a wake from the Item change feed ([announcement-records.md](announcement-records.md), "Durable triggers"), where it cannot be lost. The router's `story-published` task below is the old alert path: its trigger is gone, and PPY-58d962 replaces it with the email Delivery of an Announcement.

The router reads the published item, drops it unless some list's rule matches (`sections`, `tags`, `types`, as for the newsletter), and hands Caducus a `story.published` event whose id comes from the lineage and which names the matching lists. Caducus dedupes on that id in the site's table, so a publish, unpublish and publish again mails once. The event fans out page by page over the `byList` index through the email queue; a reader on several matching lists gets one message.

## Readers: Caducus public audiences

The kind `story.published` (`src/papyrus_content/notifications/data/notification-kinds.json`) is class `public`: its audience is the readers who subscribed to the matching lists and confirmed. Readers, lists, consent evidence, suppression, tokens and abuse limits are Caducus's (`caducus.notify.audience`, [docs/public-audiences.md in AnthusAI/Caducus](https://github.com/AnthusAI/Caducus/blob/develop/docs/public-audiences.md)); the plugin builds the audience from the site's settings (`public.py`, `links.py`) and hands each reader action to `caducus.notify.handlers.public.dispatch`. The operators parameter no longer receives new stories.

- **Routes.** `/api/notifications/{subscribe,confirm,preferences,unsubscribe,state}` (`lib/notifications-api.ts`): the same-origin rule, 400 and 303 rather than 403 and 404 because the edge rewrites those, and a site without the plugin answers 404. Subscribe answers `202 check_email` for anything valid-looking, `400 invalid_email`, `invalid_lists` or `invalid_consent` (the wording is not the configured `consent`), and `429 slow_down` when one network sends far more than this site's readers do. The route passes the site origin to the function as consent evidence.
- **Confirmation.** One themed message with a button to `<base>/notifications/confirm/?token=`; the page's button POSTs. Nothing else is sent until the reader confirms; the link works for `confirmWindowHours`, and an unconfirmed address is deleted then (DynamoDB TTL).
- **Story mail** carries `List-Unsubscribe` (the one-click URL `/api/notifications/unsubscribe?t=&l=`) and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, and a footer with the reader's preferences and unsubscribe page links and the postal address. Links carry a signed token, never an address.
- **Bounces and complaints.** The `-ses-` function passes a permanent bounce or a complaint to Caducus, which suppresses the reader and unsubscribes them from every list. A reader who turns a list on again from their manage link lifts it, and the router also removes the address from the SES account suppression list.
- **Erasure and export.** A reader deletes their data from the preferences page. Admin export and erasure are Caducus calls (`PublicAudience.export` and `erase`) that no public route sends; the newsroom panel that calls them with the admin group checked comes with PPY-6b2d35.

## List cadence, time and rule as data (PPY-4d74d9, slice N1)

A list's cadence is data, not code. The site's `lists` document (a versioned site document kind, `src/papyrus_content/list_cadence/`; only an admin who is a person changes it, each change with a reason) holds, for each list id: `cadence` (`each`, `daily` or `weekly`), `sendAt` (`{time, day}`, the weekday for a weekly list) and `timeZone` for a periodic one, `rule` (sections, types, tags and `minStars`, three to five: a lower number is refused), `requireReviewedSource`, `workingDocument` (`story` for a weekly issue that is published to the archive, or `delivery`), `template`, `agent` (the automation whose wake runs the list) and, optionally, `rung`. A list's own rung can only narrow the site policy's rung for it.

- **Schedule.** `papyrus agents schedules` (the deploy step) reads the document and keeps one entry in the site's schedule group for each periodic list, `agent-list-<id>`, in the list's local time and zone. A new list, a changed time or a removed list needs that reconcile and nothing else. A list whose agent is not an agent of the site, or is switched off, is refused by name.
- **Wake.** A tick wakes the list's agent with the wake key `<agent>:list:<list>|schedule|<time>` and the input `listId` (`wake.run_list`). An every-item list has no clock: the Item change feed wakes the announce agent when a page goes live or a rating changes (`story_wake.run_story_wake`, which re-reads the Story and calls `wake.run_story_change`; PPY-e3bb2b, [announcement-records.md](announcement-records.md#durable-triggers-ppy-e3bb2b)).
- **Records.** Every cadence makes one Announcement and one email Delivery of the same shape (`announce.py`): `roundup:<list>:<local week or date>` for a periodic list, `story-published:<lineage>` for every-item lists (one Delivery whose audience is every list that carries the Story). Changing a list's time changes the next tick only: a period that has its Announcement keeps it.
- **Periods and what carries forward (PPY-b71153, slice N3).** The key's period is the list's local date or ISO week of the time the tick was *scheduled for*, never the time the run happened or UTC, so a late run, a tick delivered twice and a clock change each leave one issue for the period (the scheduler's own zone support moves the instant; the local date it falls on is the period). An item is eligible for the next issue when it qualified since the list's last *sent* Delivery: `wake.run_list` reads the sending account's Deliveries newest first (`periods.read_history`, stopping at the list's last sent one) and hands `since` to `candidates_for`. Once a period's Announcement exists, each earlier issue of the list that never went (planned or released, its email waiting, failed or blocked) is cancelled with the reason "not released before the next period; items carried forward" and its email withdrawn (`Announcements.cancel_unsent`); a retry after a crash finishes the cancelling. An issue that is sending or sent is never cancelled. Specs: `features_backend/period-keys.feature`.
- **An empty period (PPY-1d451f, slice N4).** A period with no item that reached the list's bar and no words a person wrote (`notes_for`, handed to `wake.run_list` like `candidates_for`) makes nothing: no Announcement, no Delivery, no email. The run's output is `Result.declaration()`, which the procedure returns so the runner records `nothing` with the reason code `no_items_reached_bar` (the words are `Result.reason`), and Today shows it beside the mark and "Nothing to do". A list's `emptyPeriod` is `nothing` (the default) or `draft_only`: the second makes the period's Announcement (about no Story yet) and a draft email with no words and no words file, which `mark_ready` and the attempt guard both refuse, so it cannot go by itself and no placeholder is ever sent. A person writes into it with `wake.write_note`, which gives the same Delivery its first words (`Deliveries.write_words`: an edit, not a correction, because nothing was sent; the Delivery becomes ready at the approval the rung gives); an agent's words are refused. A person's note written before the tick makes the period an issue in the same way. Below `prepare` nothing is made, as for any list. Specs: `features_backend/empty-period.feature`.
- **Cadence families (PPY-a19b9d, slice N2).** Lists that carry the same items at different cadences (every item, daily summary) name the same `family` in the list settings; a list that names none is its own family, so the curated weekly newsletter is untouched by a reader's choice elsewhere. A family has one list for each cadence and at most one periodic list (the settings refuse more). The rule belongs to Caducus (0.4.0, [public-audiences.md](https://github.com/AnthusAI/Caducus/blob/develop/docs/public-audiences.md)): Papyrus passes `AudienceList(family=...)` and a `move_effective_at` hook (`public.py`, `list_cadence/family.mover`) and the stock `PublicAudience` applies it where a reader's lists are written, so subscribing, confirming, saving preferences, importing and the one-click unsubscribe all hold it. Asking for two new lists of one family at once answers 400 `one_cadence_per_family` (an import answers `refused`); choosing a list of a family the reader holds another of moves them. **A move takes effect at the next period start** of the family's periodic list (`family.next_period_start`: the next scheduled time on the list's local calendar); a family with no periodic list moves at once. Until then the reader stays on the list they were on and the preferences page already shows their choice, so an item published after a noon switch and before the next period start reaches them through the old list, and their first summary of the new list covers the period that starts then: every item reaches the reader by exactly one route. Each membership row records `since` and, once moved off, `until`. An every-item Delivery goes to the members at the moment it is sent. A periodic Delivery goes to the members at its period's start: `CaducusEmail.submit` puts `audienceAsOf` on its event (`family.period_start` of the Delivery's release time, one period before it on the list's local calendar), Caducus keeps it on the fan-out, and a reader who has moved off since still gets the summary they were due. An every-item Delivery omits it. The function's list settings (`LISTS_JSON`, from the plugin's `lists`) carry `family`, and for a periodic list `cadence`, `sendAt` and `timeZone`, the names the site's `lists` document uses. Specs: `features_backend/cadence-family.feature`.
- **Not built here.** The agent procedure that supplies the period's Stories and drafts the words, the working document (issue Story) and the Caducus fan-out are later slices; the records above are made, nothing is sent. Specs: `features_backend/list-cadence.feature`.

## Reader pages (PPY-f361ee)

A reader subscribes, confirms and manages notifications on real pages of the site, in its own header, theme and footer (light, dark, phone), never on an `/api` address. When `notifications` is in `PAPYRUS_PLUGINS`, the standard projector writes seven pages (`src/papyrus_content/projection/standard/notifications_pages.py`, modelled on the newsletter's pages in [newsletter.md](newsletter.md)):

| Page | Purpose |
|---|---|
| `<base>/notifications/` | Subscribe: the `<papyrus-notifications>` web component |
| `<base>/notifications/confirm/` | Confirm button for the emailed link |
| `<base>/notifications/confirmed/` | Subscribed, with a link to manage |
| `<base>/notifications/preferences/` | Manage: one button per list that is On or Off, Save, Unsubscribe from everything, Delete my data (with a confirm step) |
| `<base>/notifications/unsubscribe/` and `unsubscribed/` | One-click landing page and its result |
| `<base>/notifications/expired/` | A link that is no good; points back to the subscribe page |

They are always the directory form (`notifications/confirm/index.html`) whatever `urls.style` says, because the emails and the `/api/notifications/*` redirects use those exact addresses. They are `noindex`, carry `<meta name="referrer" content="same-origin">` (so form posts send the site's real `Origin`), and have no Markdown twin and no place in any sitemap, `llms.txt`, `llms-full.txt` or feed. A reconcile never deletes pages under `notifications/` unless the verified deployed plugin list lacks `notifications`. A site without the plugin has none of them.

- **Scripts (external, no inline script or style, so a strict CSP is fine).** `/_plugins/papyrus-notifications-pages@1.js` (every page) reads `token`, `list`, `lists`, `msg` and `step`, fills the hidden `t` fields and fetches names and state from `/api/notifications/state`; `/_plugins/papyrus-notifications@1.js` (the subscribe page only) defines `<papyrus-notifications>`, which reads the offered lists with `GET /api/notifications/state?kind=offered` (the site's public list settings, nothing about any reader) and posts to `/api/notifications/subscribe`. The component shows the site's `consent` setting from that same answer, exactly, and posts it back (the function refuses any other wording); it has no `consent` attribute. Attributes: `lists`, `endpoint`, `state`, `form-id`, `label`, `button`, `success`. Without JavaScript a page says "This page needs JavaScript." and shows no form.
- **Analytics events (PPY-5a1607).** On a site that sets a GA4 measurement id (`chrome.ga_measurement_id`, never on a staging or otherwise guarded build) every page also loads `/_plugins/papyrus-notifications-analytics-v1.js` first. It sends `subscribe_start`, `subscribe_submitted`, `subscribe_confirmed`, `preferences_changed`, `unsubscribe` and `subscribe_error` through the site's own `gtag`, so Consent Mode decides what leaves the browser, and from the page only, never from the server. A site without an id loads no event script. The events, their parameters and what they never carry are in [site hosting](site-hosting.md#subscription-and-notification-events); there is no `issue_open` event (opens would need a tracking pixel, which the email renderer forbids), and visits to the archive are measured by their own page views.
- **Design.** Buttons, never dropdowns; Lucide icons only; flat fills, no borders (`.markus-notifications-*` in `markus-components.css`, fills mixed from the text colour so both themes work). State is a word and a mark, never colour alone: a list is `On` with a bell or `Off` with a bell-off, and every status line has a check or alert mark and words. After saving, the page says in words what the reader gets ("Your choices are saved. You get: New stories.").
- **Bad link or service down.** A token the function rejects (400) goes to the expired page with `location.replace`; a service that cannot be reached (502, 503, network) is said in words ("Notifications are not available right now. Please try again later.") and is not called expired. The subscribe form says a network limit (429 `slow_down`) in words too: "Too many signups from your network just now. Please try again later."
- **Not built (decided).** The Slack and Discord sign-in option waits for those channels to be live (PPY-cc015c, PPY-62c937) and for a public-reader site; nothing renders for it today.
- **Rollout.** Enabling the plugin on an existing site needs one full projection to write the pages. Screenshot review with Ryan, Machines on Machines first, comes before any prod rollout (PPY-e28679).

## Moving a site's newsletter subscribers here (PPY-6b2d35)

Notifications owns subscribers, consent and suppression; the newsletter plugin stops owning them. A site that sends through the newsletter plugin (Shipped, Distinctive Mark) moves its readers with one operator command, once per site, and is then switched in one deploy that also bumps what it needs. MoM never has a newsletter table. The code is `src/papyrus_content/notifications/migration.py` (steps), `migration_cli.py` (command) and `legacy_links.py` (old links); specs `features_backend/notifications-subscriber-migration.feature`, tests `migration_test.py`.

- **What moves.** Every confirmed subscriber and every suppressed address that has a profile. A subscriber's lists keep their ids: the newsletter's alert lists are `story.published` lists in the notifications settings, and its roundup list is a list with `kind: "roundup"` (no rule; a roundup list is never sent each story, `events.matching_lists`). Consent evidence (the original record, every field) is copied by Caducus's `import_subscriber` and marked `source: "migrated"`, `from: "newsletter"`; no confirmation or any other mail is sent. A bounce, complaint or manual suppression is written as such and no list is indexed for it, so the address is never mailed. Not carried: a pending signup (never consented), an address that unsubscribed, and a suppression row whose profile is gone (it holds no address; SES's account suppression list, which both systems share, still blocks it).
- **The command.** `python -m papyrus_content.notifications.migration_cli plan|run|verify --newsletter-table <table>`, with the notifications function's own environment exported. `plan` and `run --dry-run` only read: counts per list (confirmed, pending, unsubscribed), consent coverage, suppressed addresses (masked), what is and is not carried, and `PROBLEM` lines that stop a real run (a list the notifications settings do not declare; a confirmed subscriber with no consent evidence, which is never invented). `run` writes, so it needs `--sends-frozen` (the agreed freeze of the site's newsletter sends is on) and `--old-links-until YYYY-MM-DD`; it is idempotent (a second run reports every subscriber `unchanged` and writes nothing) and it settles anyone who stopped on the newsletter since an earlier run (their lists are ended in notifications too). `verify` compares source and target subscriber by subscriber and prints counts per list, suppressed addresses, consent records and old-link aliases; it exits 1 unless every one matches. An address that erased itself in notifications is refused by Caducus and never comes back.
- **Old links.** Mail already sent carries manage and unsubscribe tokens in the newsletter's format. The run writes `ALIAS#newsletter#<old subscriber id>` for each subscriber, expiring at the end of `--old-links-until` (DynamoDB deletes the rows). While the plugin setting `legacyNewsletterLinks` is on, the router verifies an old-format token (signed with the key the newsletter plugin generated; its SSM parameter is retained when that plugin is removed, and the router functions may read it) on the four manage actions only (`preferences_state`, `update_preferences`, `unsubscribe`, `delete_subscriber`) and swaps it for the subscriber's new manage token; an old confirm token is never accepted. It is a dated step, not a standing compatibility path: the retirement change deletes `legacy_links.py`, its two call sites, the setting and its IAM grant (the module's docstring lists them), once the date has passed and the move is verified on every site.
- **Not built here.** The old page addresses (`/newsletter/preferences/`, `/newsletter/unsubscribe/`) and the old one-click endpoint (`/api/newsletter/unsubscribe`) are the newsletter plugin's; once it is removed from a site they must lead to the notifications pages and `/api/notifications/unsubscribe` with the token untouched, which is front-end work tracked on the ticket. The newsletter plugin's subscriber, consent and suppression code is deleted in the change after both sites are verified (the `@wip` scenario "One owner").

## Sending as the site

Notifications reuse what the site's newsletter sending stack ([infra/newsletter](../infra/newsletter/README.md)) created in the same account: the SES identity for `sendingDomain` and the configuration set `papyrus-<siteId>`. No sending authorization, no second set, no central sender. One set means one reputation and one pause per site.

- **Which sites have an identity.** [config/newsletter-sending-identities.json](../config/newsletter-sending-identities.json) lists every site under `infra/amplify-app-shell/examples` with its sending domain or `null`, and `scripts/test-sending-identities.ts` fails when a site is missing from it. On 2026-11-04 the sites with no stack were Anth.us and Threat Intelligence (and the Pretext example). Deploy the stack for a site before enabling the plugin there.
- **Tags.** Every message carries `site`, `kind` and `delivery` (`SiteMailer` adds `site`; Caducus adds the other two). The newsletter's event handler already ignores any event without a valid `sub` tag, and this plugin ignores any event whose `site` tag is not its own or that has no `delivery` tag, so the two consumers of the set's events never touch each other's mail (`features_backend/notifications-site-identity.feature`).
- **Events.** The SES event rule needs the stack's `EventTransport` set to `both` (the newsletter keeps its SNS topic; the default bus gets the same events). The `-ses-` function maps a message back to its delivery through a `MSG#<messageId>` row written when the message is sent, and moves the delivery to `delivered`, `bounced` (permanent), `delayed` (transient bounce or delay), `complained` or `rejected`. A status never moves backward, because SES delivers out of order.
- **Pause.** A site with the newsletter plugin keeps its alarms and pause. A site with notifications only gets the same two rate alarms from this plugin, and the `-pause-` function turns sending off on the configuration set when either enters ALARM. Nobody pauses by hand and nobody resumes automatically: lifting a pause is `aws sesv2 put-configuration-set-sending-options --configuration-set-name papyrus-<siteId> --sending-enabled` by a person, after reading why. Admins are told by the account's operator listener, which reads every alarm on the default bus.
- **A send on a paused set** is refused by SES with `SendingPausedException` (listed for `SendEmail` in botocore's sesv2 service model; `SiteMailer` catches only that `ClientError` code). The delivery is logged `failed` with the reason `sending is paused for configuration set papyrus-<siteId>` and is not retried. The AWS documentation describes the exception for the account's sending; that it is also what a paused configuration set returns is confirmed by the first forced pause on Machines on Machines (any other code surfaces as a retried delivery, and the dead letter alarm tells admins).
- **Footer.** The postal address comes from SSM exactly as for the newsletter (`/papyrus/<siteId>/email/postal-address`, else `/papyrus/email/postal-address`). The confirmation (account class) prints none. Public-class mail (story mail to readers) is refused with the reason `postal address missing` when neither parameter holds one, and otherwise carries the address in the footer with the reader's own manage and unsubscribe links.
- **Capacity** is shared by the account (14 messages a second and 50,000 a day on the 2026-11-04 reading). Each site's pacer reads `MaxSendRate` and cannot see the others, so Caducus's throttling backoff keeps them honest; watch it on batch sends. There is no fixed cap: ramp Machines on Machines first, then the rest.

## Turning it on for one site

1. The site's sending stack exists (`newsletter-sending-identities.json`; if the domain is `null`, deploy it first, see [infra/newsletter](../infra/newsletter/README.md)) and its `EventTransport` is `both`, so the SES-event rule has a destination (the newsletter keeps working on the topic).
2. Add the plugin block above to the site's `papyrus.config.ts`.
3. Put the postal address parameter (public mail is refused without it). The operators parameter stays for operator-class kinds.
4. **The forced pause drill has passed** on a test configuration set (PPY-a85725): with the set's sending off, a send to the SES simulator shows the delivery `failed` with "sending is paused", which confirms the `SendingPausedException` code `SiteMailer` relies on; with sending on again, the next send goes out. Until then no site lists the plugin with readers' lists.
5. Deploy the site's backend once (a normal backend deploy: one new stack and one new environment variable on `content-actions`).
6. Acceptance on Machines on Machines: a real inbox shows SPF, DKIM and DMARC pass; an SES simulator bounce (to the SES bounce simulator mailbox) shows `bounced` in the site's delivery log and leaves the newsletter's ledger alone.
