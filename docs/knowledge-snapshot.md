# Knowledge snapshot

The knowledge snapshot is the public, read-only data of a site's knowledge: which entities its published items mention, how often per week, what is moving, and which topic clusters have been named. One command writes it to the site store as JSON under `_data/knowledge/`; page blocks and Markus directives read it. Status: Beta. Code: `src/papyrus_content/knowledge_snapshot/`. Initiative PPY-428252.

Nothing in the snapshot is generated by a language model at read time, nothing is fetched by the browser, and nothing changes between two runs on the same records unless the records changed.

## The pipeline

Everything heavy runs on a workstation. Papyrus stores only small rows and writes only small JSON.

1. Export the published items of the site to a Biblicus corpus with `papyrus knowledge corpus export --out DIR` (item id, slug, url, `publishedAt`, tags, entities in the front matter). The whole weekly run, command by command, is in [knowledge-workstation-run.md](knowledge-workstation-run.md).
2. Run Biblicus on the workstation: topic modelling, `analyze topic-trends --bin weekly`, `analyze topic-identity` (stable cluster ids across runs) and `extract typed-entities`.
3. `papyrus knowledge publish-run --identity FILE --trends FILE --entities FILE` imports the run into the backend. It is a dry run until you add `--apply`.
4. Someone reviews with `papyrus knowledge entities ...`, `papyrus knowledge clusters ...` and `papyrus knowledge relations ...`. For now an AI agent does this; later people will. Every review command says who: `--actor ai|human`.
5. `papyrus knowledge snapshot` reads the backend and writes `_data/knowledge/`.

## Who accepted it

An AI agent is the accepting party for entities, clusters and wiki pages for now; people will take over. The backend records who for each accepted entity and cluster, and who edited each description, as `{"actor": "ai" | "human", "name": str | null, "on": "YYYY-MM-DD"}`. The snapshot publishes it (`acceptedBy`, `description.editedBy`) and the components print it ("Accepted by AI", "Edited by AI on 2026-10-21", "Reviewed by Ada on 2026-10-21").

- Every review command (`entities accept|reject|rename|describe|alias|retype`, `clusters accept|name|reject`, `relations accept|reject`) requires `--actor ai|human`. There is no default. `--actor-name NAME` is optional and never an email address.
- Entities that came from the front matter of published items were entered by an AI research agent, so `publish-run` records them as accepted by `ai` (never `human`). `--actor-name` on `publish-run` names that agent.
- Accepting again as a different actor (a person after the AI) replaces the record; the same actor and name twice changes nothing.
- A description is `reviewed` only when a person edited it, `ai_edited` when an AI agent did, and `draft` when it has text but no recorded editor. The concept of the week takes `reviewed` and `ai_edited` descriptions.
- Where it is stored (no schema change): a node's `changeReason` holds `papyrus-knowledge-review@1:` and one JSON object (`acceptedBy`, `rejectedBy`, `descriptionEditedBy`); a cluster's proposal `summary` object holds `acceptedBy`; a relation's `metadata` holds `acceptedBy` or `rejectedBy`.

### `publish-run`

```bash
papyrus knowledge publish-run --identity identity.json --trends trends.json --entities entities.json --corpus-key shipped --category-set <id>
papyrus knowledge publish-run ... --apply          # writes the plan
papyrus knowledge publish-run --apply              # front-matter entities only
```

Options: `--identity FILE`, `--trends FILE` (needs `--identity`), `--entities FILE` (each optional), `--corpus-key KEY` or `--corpus-id ID` (needed for clusters), `--category-set ID`, `--skip-front-matter`, `--actor-name NAME` (the AI research agent that entered the front-matter entities), `--confirm-resolved`, `--json`, and the operator lane options below.

What it writes, and nothing else:

| Source | Rows |
| --- | --- |
| `entities` in the front matter of a published item | An `accepted` `SemanticNode` per entity, recorded as accepted by `ai`, and a `mentions` `SemanticRelation` (item to node) with `metadata.linkSource` `front_matter` and `metadata.confirmed` true. They were entered by hand, so they count at once. |
| Entities extracted by Biblicus | A `proposed` mention makes a `generated` `SemanticNode` (unless the name resolves to a node that exists); a `resolved` mention links to the node its `entity_key` names. The `mentions` relation has `linkSource` `extractor` and `confirmed` false. With `--confirm-resolved`, a `resolved` mention of a node that is already accepted is created confirmed (`confirmedBy` is the AI actor "extractor resolution"). Created once; a later run never changes them. |
| Typed relations of the extractor | A `SemanticRelation` between two nodes (predicate is the relation type, `confirmed` false) when both nodes are accepted at the time of the run. A relation with an endpoint that is not accepted yet is counted (`relationsSkippedUnaccepted`) and picked up by a run after the endpoint is accepted. Only an accepted relation becomes a neighbour in the snapshot. |
| Clusters | One `SteeringProposal` per cluster uid (`proposalKind` `topic_cluster`, `steeringDomain` `topics`, `status` `proposed`). |

Rules:

- A name resolves to an existing node of the same kind by case and white-space insensitive name or alias. A matching `generated` node named in the front matter becomes `accepted`. A `rejected` node is never revived or linked.
- Removing an entity from the front matter supersedes its `front_matter` link on the next run.
- Ids are deterministic and the compare ignores timestamps, so a second run with the same input plans only no-ops.
- A continued cluster has the same uid, so the run updates its figures in the same proposal and keeps its status, name, review fields and `acceptedBy`.
- The proposal model has no field for run figures, so they ride in `summary` as one JSON object with the marker `papyrus-knowledge-cluster@1` (uid, event, predecessors, top terms, weekly series, earliest publication, member count, run id and date, `acceptedBy`). `description` holds a readable sentence and `evidenceItemIds` the member item ids.
- `publish-run` never calls a language model and never touches the site bucket.

### The Biblicus files

`run_input.py` maps the Biblicus outputs onto Papyrus's own pydantic models; unknown fields are ignored. Each file is named on the command line.

- `--identity`: `<corpus>/analysis/topic-identity/<run_id>/output.json` of `biblicus analyze topic-identity` (`run_id`, `generated_at`, `trends_snapshot_id`, `series_iso_weeks`, and `clusters[{uid, topic_id, event, predecessor_uids, label, top_terms, member_item_count, member_item_ids, first_seen, earliest_published_at, weekly_series}]`).
- `--trends`: `<corpus>/analysis/topic-governance/<snapshot_id>/output.json` of `biblicus analyze topic-trends --bin weekly`; only `snapshot_id` and `weekly_bins` (`as_of`, `iso_weeks`, `discovered_topics` and `canonical_topics` as `{topic_id, topic_uid, counts}`) are read. A cluster takes the series whose `topic_uid` is its uid, else whose `topic_id` is its `topic_id`. Without this file, or when it is from another trends snapshot than the identity run used (a warning says so), the cluster keeps the eight weekly counts of the identity file.
- `--entities`: the output of `biblicus extract typed-entities`: `items[{item_id, entities[{id, kind, text, state, entity_key, span, score}], relations[{id, type, subject, object, state, span, score}]}]`. `subject` and `object` are ids of entities of the same item. `item_id` is the id of the Papyrus item (the corpus export writes it to the front matter); a mention of an item that is not published is counted and skipped.

The run date is the trends `as_of`, else the date of `generated_at`.

### Review

```bash
papyrus knowledge entities list --status generated --counts        # also: --kind, --query, --import-run, --limit, accepted, rejected, all
papyrus knowledge entities accept --key task--voice-cloning --actor ai --actor-name "Research agent"   # --keep-links-unconfirmed to leave its extractor links alone
papyrus knowledge entities reject --key task--voice-cloning --actor ai
papyrus knowledge entities rename --key task--voice-cloning --name "Voice cloning" --actor ai
papyrus knowledge entities describe --key task--voice-cloning --text "..." --actor human --actor-name Ada
papyrus knowledge entities alias --key maker--mistral-ai --add Mistral --actor ai    # another name for an accepted entity; the extractor resolves it next run
papyrus knowledge entities retype --key platform--swe-bench --kind benchmark --actor ai    # fixes a wrong kind; --dry-run shows the plan
papyrus knowledge entities registry --out registry.json --vocabulary vocabulary.yml   # the typed extractor's registry: every accepted entity with all its names

papyrus knowledge clusters list                                    # --status proposed|accepted|rejected|all
papyrus knowledge clusters accept --uid <cluster uid> --name "Voice cloning" --actor ai
papyrus knowledge clusters name --uid <cluster uid> --name "Voice cloning and TTS" --actor ai
papyrus knowledge clusters reject --uid <cluster uid> --actor ai

papyrus knowledge relations list                                   # --state proposed|accepted|rejected|all
papyrus knowledge relations accept --id <relation id> --actor ai
papyrus knowledge relations reject --id <relation id> --actor ai
```

`--key` takes a node key, an id or a lineage id. These commands write at once; add `--dry-run` to preview. A node is edited in place, so links stay valid. `entities accept` also confirms the node's extractor links, because the snapshot counts only confirmed links. `rename` keeps the old name as an alias and keeps the node key, so public keys and URLs do not move. `describe` sets the description and records who edited it. A cluster is a `topic_cluster` proposal: `clusters accept` names it (a name is required the first time) and records who accepted it; `papyrus knowledge topics review-proposal` refuses these proposals and points here.

**Aliases.** `entities alias --key K --add NAME --actor ai|human` adds NAME to the accepted entity's aliases and records the actor (`aliasedBy`, with the day, in the node's `changeReason`). Use it for a duplicate you rejected, such as `Mistral` next to the accepted `Mistral AI`: once `Mistral` is an alias, the next `registry` carries it, the extractor resolves the mention to the accepted node, and a later import links it there. Nothing changes when the node already answers to the name; a name that another live node of the same kind holds is refused (merge those by hand); a rejected node holding the name does not count. The command refuses an email address and a rejected target.

**Kinds.** A kind is kept exactly as the Biblicus vocabulary key writes it, with underscores (`model_family`), in nodes, the registry and the snapshot (`kind`, `kinds[].key`). Only the entity key folds the kind to hyphens (`model-family--tern-3`). Nodes written before this stored the hyphenated form (`model-family`); they are not rewritten. Everything that compares or reports a kind (resolving a mention, the snapshot, the registry, `maker-kind`) treats `model-family` and `model_family` as one kind, so those nodes still match and the snapshot already reports `model_family`.

**Retyping.** The kind is part of the key (`platform--swe-bench` is `kind--name`), and the node id and lineage id derive from the key, so `entities retype --key K --kind KIND --actor ai|human` cannot edit the kind in place. It migrates the entity instead: a new node is created under the new key (`benchmark--swe-bench`) with the same name, aliases, description, status and acceptance record, and `retypedBy` (the actor and the day) recorded in its `changeReason`; the old node is superseded (`versionState` and `status` `superseded`), so it is no longer current, is never resolved by a later import and drops out of the snapshot, whose next run deletes its entity file; and every current relation that touches the old node, item mentions and relations between entities alike, is superseded and re-created on the new node with the same metadata, so confirmed links stay confirmed and an accepted relation stays accepted. Relation ids derive from their two ends, so the plan is repeatable. The command is refused when the node is rejected, already has that kind, or a current node already holds the new key (merge those by hand). The old key stops existing: public URLs and wiki pages built from it need the new key, so run `snapshot` and `wiki sync` afterwards.

**Model and model family.** `model` (a specific named model, label "Model") and `model_family` (the line of models above it, label "Model Family") are separate kinds, in nodes, the registry, the snapshot's `kinds` and the wiki page text. A model is related to its family with `member_of` (subject: the model, object: the family; seeded in `corpora/papyrus-semantic-relation-types.yml`). Like every extractor relation it is published as a proposal and shows as a neighbour of both ends once a reviewer accepts it. A model with no accepted `member_of` simply has none.

**The extractor's registry.** `entities registry --out FILE [--vocabulary FILE]` writes the JSON list `biblicus extract typed-entities --registry` takes: one entry per accepted entity, `{key, kind, aliases}`, where `aliases` holds the display name and every alias the node has (a rename keeps the old name as an alias, so `Mistral` and `Mistral AI` both resolve when the node holds both). The extractor refuses an alias that belongs to two entities, so such an alias (compared the way the extractor does: case folded, every run of other characters one space) is left out of all the entities that claim it and printed as a warning on stderr; that mention is then proposed, not guessed. `kind` is always the underscore form (a node stored as `model-family` is written as `model_family`). With `--vocabulary FILE` (the Biblicus vocabulary, its `entity_kinds` keys) the kind is the vocabulary's own key, and an entity whose kind the vocabulary does not have is left out and printed as a warning, because the extractor refuses a registry with a kind outside its vocabulary. Stored nodes are never changed by the command.

**Topic configuration.** `papyrus knowledge topic-config --out FILE [--stop-words FILE]` writes the fixed BERTopic configuration of [the workstation run](knowledge-workstation-run.md) with the vectorizer that keeps cluster top terms readable. See there.

## `snapshot`

```bash
papyrus knowledge snapshot --out ./site-out                              # local directory
papyrus knowledge snapshot --site-bucket <bucket> --reproject            # the site store, then re-project the pages
papyrus knowledge snapshot --records records.json --out ./site-out       # offline, from a records file
```

Options: `--as-of YYYY-MM-DD` (default: the Monday of the current ISO week, UTC), `--static-dir DIR` (the site's static directory, the projector needs it to place item URLs), `--reproject`, `--allow-deletions` (only with `--reproject`; see below), `--unaccepted-clusters hide|unnamed` (default `hide`), `--entity-href TEMPLATE` (a site-relative request path such as `/wiki/{slug}/`; `{key}` is the entity key and `{slug}` is the key with `--` folded to `-`, which is where a wiki page of that entity lives; the path gets the base path in front of it; a template that already starts with the base path, or an absolute URL, is taken as written; without it `href` is `null`), `--cluster-href TEMPLATE` (`{uid}`, `{slug}`; same rule), `--maker-kind KIND` (default `maker`), `--concept-kinds k1,k2` (the kinds the concept of the week may come from; default every kind), `--beats-config FILE` or `--beats-category-set ID` with `--beat-href TEMPLATE` (same rule), `--json`.

Files are written through the same writers as the projector, under the site's `urls.basePath` (a site served at `dataparade.io/posts` has `posts/_data/knowledge/`, and the projection reads it from there), as `application/json` with the short `s-maxage` cache of non-hashed files. A file whose bytes are unchanged is not written; entity files that no longer have an entity are deleted; what changed is invalidated on CloudFront. `--reproject` then runs the same re-projection as `papyrus ops content project --all`, so prerendered pages pick up the new numbers. The reconcile never deletes `_data/knowledge/`.

`--reproject` refuses to run when the re-projection would delete the pages of an item that stays published, or more than a tenth of the stored pages (and more than 20). The projector decides which pages each published item has from the site's `projection.json`, so a checkout of the site that is out of date can leave published items with no pages, and the projection would delete everything remembered for them. The refusal happens before anything is written; it lists how many pages are affected per top-level path, the published items concerned and the first 50 page keys, and exits 2. Check that `--static-dir` is a current checkout of the site; pass `--allow-deletions` only if the deletions are intended. When `--static-dir` is a git checkout with an upstream branch, the command also runs `git fetch` and prints a warning on stderr if the checkout is behind (`warning: --static-dir DIR is N commits behind origin/main; ...`). The warning never stops the run.

### Beats

A beat is a site topic. There is no beat unless you choose a source: `--beats-config` takes a `topics` mapping like a site's `web/scoring.json` (`{key: {label, path}}`; an item belongs to the beat whose key is one of its front-matter `tags`); `--beats-category-set` takes the accepted root categories of a category set (an item belongs to a beat when it is a member of the accepted cluster the category came from, or carries the category key or name as a tag). `topicCount` is the number of beats.

## File shapes (`schemaVersion` 1)

Output is deterministic: keys sorted, no timestamps, `asOf` is the given date. A test pins the exact field set of each file and fails when a field is added.

`index.json`: `schemaVersion`, `asOf`, `entityCount`, `topicCount`, `kinds` (`key`, `label`, `count`), `beats` (`key`, `name`, `href`, `itemCount`, `series8`, `topEntities`: entity keys, the accepted entities linked to the most of the beat's items, at most 12), `entities` (`key`, `kind`, `name`, `aliases`, `href`, `acceptedBy`, `itemCount`, `weeksOfHistory`, `series8`, `change`, `isNew`), `trending` (entity keys), `conceptOfTheWeek` (`key`, `name`, `href`, `lede`, `editedBy`, `itemCount`, `makerCount`, or `null`).

`entities/<key>.json`: `schemaVersion`, `key`, `kind`, `name`, `aliases`, `acceptedBy`, `description` (`state` `reviewed|ai_edited|draft|none`, `editedBy`), `href`, `itemCount`, `weeksOfHistory`, `series8`, `series26`, `change`, `neighbours` (`relation`, `key`, `name`, `kind`, `weight`), `relatedItems` (`title`, `url`, `publishedAt`, `reason`).

`clusters.json`: `schemaVersion`, `asOf`, `runId`, `unacceptedClusters`, `clusters` (`uid`, `beats` (keys of the beats that share published member items with the cluster), `name`, `acceptedBy`, `state` `new|growing|cooling|null`, `itemCount`, `topTerms`, `series8`, `weeksOfData`, `href`).

`change` is `{last4, prior4, percent}`. `acceptedBy` and `editedBy` are `{actor: "ai" | "human", name: string | null, on: "YYYY-MM-DD"}`, or `null` when nothing is recorded (an unnamed cluster never claims an acceptance).

## Rules

- **Public-safe.** Only `accepted` entities, only published items with a publish date, only confirmed links and relations. No reference text, private note, message body or email address is read; a name, alias, title or description that holds an email address is dropped. An entity with no confirmed link has no file.
- **Weeks.** ISO weeks, Monday to Sunday, UTC. `series8` and `series26` run oldest to newest and end with the week that contains `asOf`. An item published after that week is not counted.
- **Counts.** Items per ISO week with a confirmed link to the entity. `itemCount` is all such items up to `asOf`.
- **Change.** The items of the last four weeks against the four before them. `percent` is `round(100 * (last4 - prior4) / prior4)`, halves away from zero, and `null` when `prior4` is under 5 **or `weeksOfHistory` is under 8**. This is the one place the rule lives: the components show `change.percent` when it is there and never work it out again, so the index, the trending order and the strip cannot disagree. `last4` and `prior4` are always given. Twelve items against six is +100 percent for an entity with eight weeks of history, and `null` for one with six.
- **New.** `weeksOfHistory` counts the weeks from the first confirmed link to the `asOf` week, inclusive. Under four, `isNew` is true: no percent, and the entity is not trending. Components show no sparkline under four weeks, a sparkline without a percent from four to seven, and the full figure from eight; the 26-week chart is for twelve weeks or more.
- **Trending.** Entities that are not new and have `last4` above zero, by the displayable `percent` descending (so a young entity with a large raw growth does not outrank a mature one); entities with a `null` percent, whether for a small base or a short history, come after, by `last4 - prior4` descending; ties by key.
- **Neighbours.** Accepted `SemanticRelation` rows between two published entities (relation is the predicate), and entities that share items (relation `mentioned_with`; at most twelve, by shared items). `weight` is the number of items that link both. Neighbours are entities that are in the index.
- **Related items.** The entity's own items, newest first, at most twelve; `reason` is the entity key. `url` is the canonical path the site's projector gives the item.
- **Concept of the week.** The entity with a `reviewed` or `ai_edited` description and the most items in the last four weeks; `lede` is that description, `editedBy` says who edited it, and `makerCount` is the number of distinct entities of the maker kind linked to its items. `--concept-kinds` limits the choice to entities of those kinds, so a publication can feature a task or a technique and not a platform or a licence. `null` when no entity qualifies.
- **Clusters.** Only the latest run is published. Accepted clusters carry their name and `acceptedBy`. With `--unaccepted-clusters unnamed`, proposed clusters appear with `name` `null`. `state` is `growing` at +20 percent or more, `cooling` at -20 percent or less, `null` otherwise or with fewer than four weeks of data; `new` means the run reported the cluster as new and its earliest published member item is within four weeks of `asOf` (the date of the run does not count). The series are the run's weekly bins, so weeks after the run read as zero until the next run.

## Operator lane (IAM)

An operator without a `papyrus login` session for a site's CMS selects the IAM lane on purpose, as every operator command does (see [cli-login.md](cli-login.md) and the GraphQL auth split in `AGENTS.md`). Every knowledge command that reads or writes the CMS accepts:

- `--auth iam` (or `user`), the same as `PAPYRUS_GRAPHQL_AUTH`. Nothing else chooses a lane for you: a failed user session never falls back to IAM, and the command prints the lane it uses.
- `--amplify-outputs FILE`, the `amplify_outputs.json` of the backend to talk to (its `data.url` becomes `PAPYRUS_GRAPHQL_ENDPOINT`), so the target is named rather than found in the working directory.

Each command writes one line to stderr, `knowledge<TAB>auth<TAB>iam<TAB><appsync host>`, before it touches the backend. Check the host before you add `--apply`.

## Components

The page blocks and Markus directives that read these files are built under epic PPY-a45fd1 (the contract names `knowledge-trending-strip`, `knowledge-trending-list`, `knowledge-clusters`, `knowledge-concept-of-the-week`, `knowledge-topic-count` and `knowledge-entity`). A page renders nothing from a file that is absent.
