# Knowledge snapshot

The knowledge snapshot is the public, read-only data of a site's knowledge: which entities its published items mention, how often per week, what is moving, and which topic clusters the desk has named. One command writes it to the site store as JSON under `_data/knowledge/`; page blocks and Markus directives read it. Status: Beta. Code: `src/papyrus_content/knowledge_snapshot/`. Initiative PPY-428252.

Nothing in the snapshot is generated by a language model at read time, nothing is fetched by the browser, and nothing changes between two runs on the same records unless the records changed.

## The pipeline

Everything heavy runs on a workstation. Papyrus stores only small rows and writes only small JSON.

1. Export the published items of the site to a Biblicus corpus (item id, slug, url, `publishedAt`, tags, entities in the front matter).
2. Run Biblicus on the workstation: topic modelling, `analyze topic-trends --bin weekly`, `analyze topic-identity` (stable cluster ids across runs) and `extract typed-entities`.
3. `papyrus knowledge publish-run --run-dir DIR` imports the run into the backend. It is a dry run until you add `--apply`.
4. The desk reviews with `papyrus knowledge entities ...` and `papyrus knowledge topics review-proposal`.
5. `papyrus knowledge snapshot` reads the backend and writes `_data/knowledge/`.

### `publish-run`

```bash
papyrus knowledge publish-run --run-dir ./run --corpus-key shipped --category-set <id>            # prints the plan
papyrus knowledge publish-run --run-dir ./run --corpus-key shipped --category-set <id> --apply    # writes it
papyrus knowledge publish-run --apply                                                              # front-matter entities only
```

Options: `--run-dir DIR`, `--corpus-key KEY` or `--corpus-id ID` (needed for clusters), `--category-set ID` (the set a cluster is accepted into), `--skip-front-matter`, `--json`. It uses the signed-in CLI user (`papyrus login`, see [cli-login.md](cli-login.md)); there is no guest or IAM fallback.

What it writes, and nothing else:

| Source | Rows |
| --- | --- |
| `entities` in the front matter of a published item | An `accepted` `SemanticNode` per entity, and a `mentions` `SemanticRelation` (item to node) with `metadata.linkSource` `front_matter` and `metadata.confirmed` true. The desk typed them, so they count at once. |
| Entities extracted by Biblicus | A `generated` `SemanticNode` unless the name resolves to a node that exists, and a `mentions` relation with `linkSource` `extractor` and `confirmed` false. Created once; a later run never changes them. |
| Clusters | One `SteeringProposal` per cluster uid (`proposalKind` `topic_cluster`, `steeringDomain` `topics`, `status` `proposed`). |

Rules:

- A front-matter name resolves to an existing node of the same kind by case and white-space insensitive name or alias. A matching `generated` node becomes `accepted`. A `rejected` node is never revived or linked.
- Removing an entity from the front matter supersedes its `front_matter` link on the next run.
- Ids are deterministic and the compare ignores timestamps, so a second run with the same input plans only no-ops.
- A continued cluster has the same uid, so the run updates its figures in the same proposal and keeps its status, desk name and review fields.
- The proposal model has no field for run figures, so they ride in `summary` as one JSON object with the marker `papyrus-knowledge-cluster@1` (uid, event, predecessors, top terms, weekly series, first seen, member count, run id and date). `description` holds a readable sentence and `evidenceItemIds` the member item ids.
- `publish-run` never calls a language model and never touches the site bucket.

### Run directory

The adapter is `run_input.py`. It reads three files (the Biblicus outputs are mapped onto Papyrus's own pydantic models, unknown fields are ignored):

- `topic-identity.json`: `{"run_id", "as_of", "clusters": [{"uid", "event", "predecessor_uids", "member_count", "member_item_ids", "top_terms", "first_seen", "topic_id"}]}`
- `topic-trends.json`: the output of `biblicus analyze topic-trends --bin weekly`; only `weekly_bins` is read (`iso_weeks` and per-topic `counts`). A cluster takes the series with its `topic_uid`, else its `topic_id`.
- `typed-entities.json` (optional): `{"entities": [{"item_id", "name", "kind", "state": "resolved"|"proposed", "start", "end"}]}`

### Desk review of entities

```bash
papyrus knowledge entities list --status generated --counts        # also: --kind, --query, --import-run, --limit, accepted, rejected, all
papyrus knowledge entities accept --key task--voice-cloning        # --keep-links-unconfirmed to leave its extractor links alone
papyrus knowledge entities reject --key task--voice-cloning
papyrus knowledge entities rename --key task--voice-cloning --name "Voice cloning"
papyrus knowledge entities describe --key task--voice-cloning --text "..." --reviewed
```

`--key` takes a node key, an id or a lineage id. These commands write at once; add `--dry-run` to preview. A node is edited in place, so links stay valid. `accept` also confirms the node's extractor links, because the snapshot counts only confirmed links. `rename` keeps the old name as an alias and keeps the node key, so public keys and URLs do not move. `describe --reviewed` records `changeReason: description-reviewed:<date>`; without `--reviewed` the description is a draft. Clusters are accepted and named with `papyrus knowledge topics review-proposal --proposal <id> --action accept --display-name "..."`; the snapshot reads the name from the category that accept creates.

## `snapshot`

```bash
papyrus knowledge snapshot --out ./site-out                              # local directory
papyrus knowledge snapshot --site-bucket <bucket> --reproject            # the site store, then re-project the pages
papyrus knowledge snapshot --records records.json --out ./site-out       # offline, from a records file
```

Options: `--as-of YYYY-MM-DD` (default: the Monday of the current ISO week, UTC), `--static-dir DIR` (the site's static directory, the projector needs it to place item URLs), `--reproject`, `--unaccepted-clusters hide|unnamed` (default `hide`), `--entity-href TEMPLATE` (for example `/concepts/{key}/`; without it `href` is `null`), `--cluster-href TEMPLATE` (`{uid}`, `{slug}`), `--maker-kind KIND` (default `maker`), `--beats-config FILE` or `--beats-category-set ID` with `--beat-href TEMPLATE`, `--json`.

Files are written through the same writers as the projector, under the site's `urls.basePath`, as `application/json` with the short `s-maxage` cache of non-hashed files. A file whose bytes are unchanged is not written; entity files that no longer have an entity are deleted; what changed is invalidated on CloudFront. `--reproject` then runs the same re-projection as `papyrus ops content project --all`, so prerendered pages pick up the new numbers. The reconcile never deletes `_data/knowledge/`.

### Beats

A beat is a site topic. There is no beat unless you choose a source: `--beats-config` takes a `topics` mapping like a site's `web/scoring.json` (`{key: {label, path}}`; an item belongs to the beat whose key is one of its front-matter `tags`); `--beats-category-set` takes the accepted root categories of a category set (an item belongs to a beat when it is a member of the accepted cluster the category came from, or carries the category key or name as a tag). `topicCount` is the number of beats.

## File shapes (`schemaVersion` 1)

Output is deterministic: keys sorted, no timestamps, `asOf` is the given date. A test pins the exact field set of each file and fails when a field is added.

`index.json`: `schemaVersion`, `asOf`, `entityCount`, `topicCount`, `kinds` (`key`, `label`, `count`), `beats` (`key`, `name`, `href`, `itemCount`, `series8`), `entities` (`key`, `kind`, `name`, `href`, `itemCount`, `weeksOfHistory`, `series8`, `change`, `isNew`), `trending` (entity keys), `conceptOfTheWeek` (`key`, `name`, `href`, `lede`, `itemCount`, `makerCount`, or `null`).

`entities/<key>.json`: `schemaVersion`, `key`, `kind`, `name`, `aliases`, `description` (`state` `reviewed|draft|none`, `reviewedOn`), `href`, `itemCount`, `weeksOfHistory`, `series8`, `series26`, `change`, `neighbours` (`relation`, `key`, `name`, `kind`, `weight`), `relatedItems` (`title`, `url`, `publishedAt`, `reason`).

`clusters.json`: `schemaVersion`, `asOf`, `runId`, `unacceptedClusters`, `clusters` (`uid`, `name`, `state` `new|growing|cooling|null`, `itemCount`, `topTerms`, `series8`, `weeksOfData`, `href`).

`change` is `{last4, prior4, percent}`.

## Rules

- **Public-safe.** Only `accepted` entities, only published items with a publish date, only desk-confirmed links and relations. No reference text, private note, message body or email address is read; a name, alias, title or description that holds an email address is dropped. An entity with no confirmed link has no file.
- **Weeks.** ISO weeks, Monday to Sunday, UTC. `series8` and `series26` run oldest to newest and end with the week that contains `asOf`. An item published after that week is not counted.
- **Counts.** Items per ISO week with a confirmed link to the entity. `itemCount` is all such items up to `asOf`.
- **Change.** The items of the last four weeks against the four before them. `percent` is `round(100 * (last4 - prior4) / prior4)`, halves away from zero, and `null` when `prior4` is under 5. Twelve items against six is +100 percent.
- **New.** `weeksOfHistory` counts the weeks from the first confirmed link to the `asOf` week, inclusive. Under four, `isNew` is true: no percent, and the entity is not trending. Components show no sparkline under four weeks, a sparkline without a percent from four to seven, and the full figure from eight; the 26-week chart is for twelve weeks or more.
- **Trending.** Entities that are not new and have `last4` above zero, by `percent` descending; entities with a `null` percent come after, by `last4 - prior4` descending; ties by key.
- **Neighbours.** Desk-confirmed `SemanticRelation` rows between two published entities (relation is the predicate), and entities that share items (relation `mentioned_with`; at most twelve, by shared items). `weight` is the number of items that link both. Neighbours are entities that are in the index.
- **Related items.** The entity's own items, newest first, at most twelve; `reason` is the entity key. `url` is the canonical path the site's projector gives the item.
- **Concept of the week.** The entity with a reviewed description and the most items in the last four weeks; `lede` is that description, and `makerCount` is the number of distinct entities of the maker kind linked to its items. `null` when no entity qualifies.
- **Clusters.** Only the latest run is published. Accepted clusters carry the desk name. With `--unaccepted-clusters unnamed`, proposed clusters appear with `name` `null`. `state` is `growing` at +20 percent or more, `cooling` at -20 percent or less, `null` otherwise or with fewer than four weeks of data; `new` means the run reported the cluster as new and it was first seen within four weeks. The series are the run's weekly bins, so weeks after the run read as zero until the next run.
